# DSH

全部待核验：来自网页端调研与讨论区，只作 App 侧 harness、运行环境和认知模式的线索。

## 模型可见内容

研究观察：DSH 在请求前先写日志，再构造模型输入，并用断言保证模型可见内容能从记录重建；恢复时只回放日志。

推断：App 的上下文管理不能依赖隐藏状态。插话、状态和提示变更必须以模型能看见且可追溯的方式进入认知模式。

## 可逆副作用与运行资源

研究观察：Cordis 通过 effect 和清理路径处理插件卸载；组件耦合度提高时，卸载成本上升。DSH 的循环缺少默认的步数、token、cost 熔断。

推断：插件卸载的环境清理和运行中的资源预算是两件事。App 的预算者、上下文管理和重试策略应由 Library 组合，不能把它们混成 Kernel 机制。

## 流式输出

研究观察：DSH 把 llm/stream 与 tool/call 作为可监听流水线扩展点，并使用类型化决策组合多个策略。

推断：流式呈现、门禁和 Middleware 顺序属于 App 的组合策略。若需要保存模型生成中的状态，应使用提供者明确的在途语义，不伪造完成结果。

## 运行接缝

研究观察：Code Mode 的 worker thread 可能直接访问文件和子进程，因而绕开文件沙箱；另一种部署会显式替换为容器、无网络和只读 rootfs。

推断：App 选择模型和执行提供者时，必须明确它们的通道和隔离关系。应用组合不能把一个未受约束的执行入口当成受控文件工具。
