## 前端：驾驶舱

前端有两部分：**Principal 的驾驶舱**，与**内核的只读界面**（带一些调试能力）。这里只写第一部分。

驾驶舱是系统的一个普通参与者，受同样的权利约束，看到的是投影而不是日志，操作的是结构与权利而不是消息。这个区别决定了几乎所有的设计选择。它的特殊点：

1. 对象持续运行，默认不是请求与响应，所以前端常驻观察，随时可以介入。
2. 状态是投影，不一定是消息流。
3. 前端是根，不等于能控制一切的上帝。
4. 观察受制于 Atom 的边界，Atom 自己也可以提供一些结构。
5. 多视角、多客户端。这里涉及交互协议：每一种主体可能有自己的交互方式，这是可选字段，人类只是其中一种。

下面是从现有设计推出的几条，最后四条之前的是结构上最重要的。

### 结构从 Interface 生成，不读实现

自动生成的界面只从 Interface 出，不读 body，也不读它的 AST。理由：Interface 是唯一稳定、被别人依赖的外部模型；body 是 Implementation，别人看不到，画出来也只是猜测。这意味着放弃一个早先的想法，即用控制流提取的库把认知的内部结构画出来。

### 旁路描述不进语义，没有它也要能用

给一个 Definition 附加的界面描述（控件顺序、强调、分组）必须满足三条：不进内容寻址（否则同一份 agent 因界面不同就成了不同的身份）；构造时忽略；由前端读取，Kernel 完全不碰。没有这份描述时，前端按 Interface 生成默认布局，否则没有描述的 agent 就用不了。

### 前端本身是一个 Cognition，有自己的 Journal

驾驶舱不是一个特殊的界面层，而是一个按 Definition 行动的 Instance：持有 Port，每次点击是一次 Atom，记在自己的 Journal 里。谁在什么时候点了什么、能不能撤销，都有记录。驾驶舱与被驾驶的 agent 因此落在同一套规则里。

### 写侧的粒度是 Instance，改配置是一次 Handoff

Instance 不换 Definition，所以在界面里「改这个 agent 的配置」不是一个表单保存，而是一次构造加一次 Handoff。这决定驾驶舱的交互形状。

### 由 Reference 的规则推出的约束

- **绑定分两段**：静态的一段从 Interface 生成骨架；动态的一段在运行中把 Handle 绑到元素上。
- **Schema 到控件是一个纯函数**：value.schema 既校验，又给模型当工具说明，还能驱动界面：object 对应卡片，array 对应列表，enum 对应下拉，anyOf 对应条件渲染。
- **好看靠组件库加旁路描述，不靠生成**：生成只负责选控件和布局的正确性；控件的样子由手工组件库定；布局的顺序与强调由旁路描述定。两者不混。
- **权限就是它持有的 Reference**：界面上不显示它没有的 Reference 对应的操作。可操作的集合可以由 c-list 在运行前算出，所以「这个用户在这个 agent 上能点什么」是静态可查的，不是靠前端隐藏按钮。持有的 Correct 若是收窄过的，就只显示对应的操作；没有 Correct，界面上就没有暂停。界面按链上每一节生成可操作项，不按角色或配置。
- **投影是纯函数**：记录到视图是纯函数，所以视图可以从 Journal 离线重建，也可以对固定输入做断言。前端测试有了落点，不需要跑真的 agent。

状态：方向。

## 可视化

前端的可视化是一个独立的、很特殊的问题：用户应该控制什么？用户应该读什么？它必须全部做成扩展，比如在 Definition 旁边的标注，前提是不影响任何语义或执行，拿到的是结构，不是样式。Definition 里的章程比较容易可视化；认知需要下苦功夫。

### 原则

以下是从更早的设计里带来的、与具体对象无关的原则。它们本身是通用的可视化规则，没有对照过 Kernel 现在的对象；对象要重新映射到 Instance、Journal、Atom、Tree、来处树、派生树与 Charter 的接线图。

- **直接呈现拓扑**：领域模型本身是拓扑，可视化直接呈现它，不在它之外另造一层表示。核心结构靠图形本身（节点位置、连线方向）可见；颜色、标签与提示只是辅助，不应该要点开节点才知道类型，要看颜色才区分对象，要读标签才知道两个节点的关系。
- **投影不是第二事实源**：只消费已提交的事实，不新增持久的关系或投影状态；画布与传输层的动作不伪造领域状态（取消传输不等于取消运行）；路径一级的事实可以在总览里给摘要，但不聚合成整体的状态。
- **不补边**：不按时间、序号、数组位置、布局、名称或类型的邻近去补造关系。没有唯一来源或对齐证据时，保留已有的片段并显式标记截断，不生成端点不存在的边；折叠或聚合后的连线要能追溯到完整的来源路径。
- **不同种类的边不合并成一张图**：每个视图写明参与遍历的边与方向。权威事实、带完整查询上下文的快捷关系、纯视觉的投影（布局、聚合、命中区）是三类，用线型、标签与方向区分，每一种不伪装成另一种，非当前的关系退弱而不删除。对照 Journal 里「来处树与派生树是两种投影」。
- **三种键**：对象的稳定身份、视觉实例（同一对象可以有多个）、连续转换。预览、未提交的输入目标、分叉锚点用独立的视觉实例键，与实体共享另两种，这就是「虚影」。
- **快照加补丁等于快照**：二者经同一个归约得到相同的语义哈希（只覆盖身份、关系、状态，不含布局、时间、数组位置、相机）；带查询身份、投影版本；重复可幂等接受，乱序、缺口、过期版本不得静默接受；游标在整批归约提交之后才推进。
- **焦点相互独立**：计划焦点、运行焦点、阅读焦点、选择、输入目标、相机，不能互相推导；焦点失效时回到根，不按时间、序号或布局猜测替代目标。
- **输入目标是强边界**：提交时由后端固定成合法的位置，任务或运行只是提示；目标无效报校验错误，不静默改选最近的位置，也不在提交之后改绑；取消目标不丢草稿，提交中禁止重复提交。
- **聚合与渲染的边界**：聚合、边捆绑、布局与虚拟化不得跨关系种类、改身份或补造拓扑；虚拟化不丢焦点、可访问名称、详情的目标、输入草稿与锚点；颜色只表状态，状态与关系不只靠颜色；把「未了结」与「已到安全终态」分开显示。
- **连续性，无跳变**：展开从所属锚点附近生长，收束回同一锚点，粗表示是细表示的祖先；新意图打断动画时从当前插值状态重定向。
- **折叠深度**是同一张图的统一语义层级，不是按实体类型分栏；自适应档位按节点在屏幕上的可读尺寸决定展开深度，阈值带滞回，避免在边界反复展开收束。
- **信息承载**：气泡里放理解当前消息的局部状态；就地卡片放「这是什么、为何在这里、当前发生什么」，至多一屏；右侧面板放完整字段、事件序列、来源图、文件差异等审计内容。同一事实只有一个完整的展示位，其他位置给摘要与跳转，与本仓库「一个事实只有一处权威」是同一个思路。
- **对话是图的一种展开状态**：没有独立的对话面板，消息节点拉伸成气泡；不可继续的节点（没有检查点、调用未配对、失败的中间态）禁用输入。

### 与当前设计的接缝

这些是推断，没有验证。

- **Feed 就是读取加同一个归约**：上面的「快照加补丁」与 Plan.md 里 `apply(索引, 记录) → 索引`（写记录与重建索引共用）是同一个归约；前端的 Feed 可能就是「看」的读取（带起始序号）加这个归约，不需要新机制。
- **跨 Journal 的实时订阅**：每本 Journal 有自己的序号，驾驶舱要同时看几本，需要一个跨 Journal 的游标，现在没有。
- **折叠的坐标**：认知模式在运行时保留为一层帧，不在构造时内联展开，可视化的折叠单元与委托者观察的粒度靠它；帧由重放算出，不进记录。
- **静态骨架加运行时展开**：静态的阶段与路由供可视化，阶段内动态。只认可识别的模式（并行、流水线、循环），其余黑盒，不试图编译任意代码，不强制用户写 DSL。Lang0 在构造时本来就在 Python 的 AST 上做分析，骨架（循环、对 Port 的调用）可以从 AST 取，运行时的展开由键与 Journal 给，不需要另一份中间表示。这与上面「结构从 Interface 生成，不读实现」有张力，要定：控制流的骨架是 Interface 的一部分，还是实现细节。
- **多客户端**：读侧可以有多份「看」；写侧的粒度是 Instance，同一时刻只有一个客户端对一个 Instance 写。根的入口是求值器在系统外的 Instance，一个客户端连上就取得执行权，旧会话被拒。
- **三种视图同构**：一棵消息树，不合并时与工作树的分支一一对应，每个分支可单独运行；消息树到上下文是树到链，量级不同，需要压缩节点；文件树也要可视化并与前两者对应。三者之间的切换不跳变。
- **张力待定**：「不在领域模型之外另造表示层」与「投影、表示的层级」是否冲突，以及与上面「看到的是投影，不是日志」的关系。

### 一组设计取向

下面是更早的设计里做过的取舍，意图级，没有对照现在的对象。

- **总览回答「我有哪些工作」**：默认少量摘要，可以悬停预览或动态展开，不同时显示所有东西；默认不出现检查点、提交、步骤、消息节点。
- **两种投影，同一批对象**：以会话为中心，与以工作空间为中心；两种投影下工作空间的树都在画布最左侧；切换用非线性转场，对象顺着连线移动。
- **悬停先给轮廓**：悬停一个会话，出现横向的「虚影树」预示它内部的运行轮廓；鼠标可以移进去，再悬停某个节点看二级预览；点击是导航，点击后虚影实体化，进入主图。
- **主图自上向下生长**：分叉是真实的树结构，不设「主分支」；节点是视觉根，不是消息树的领域父节点；动画语法是生长与收束。
- **运行的折叠形式是「锚点加轨道」**：锚点保留身份与状态（运行中、暂停、完成、等待输入、中止），轨道只作弱标识。
- **文件轴分三级强度**：常态只在锚点或末端做边界徽标；叠加时出现一条与主干平行的稀疏检查点轴；审计时文件轴升为主结构。
- **目录树只在会话内、按钮开关**：范围取事实，保持真实的树；悬停图上的对象，高亮目录树里对应的路径，反之亦然，没有对应事实时不制造连接。
- **图上对话**：点击一个运行，图的最下层长出输入框，图上用明暗变化的虚影标出「现在发送会注入到这里」；点击正在运行的那条链，整条链向右拉伸成消息气泡。
- **视觉**：同源形态；颜色只表状态；运行中局部低频运动；转场强、日常弱；明暗双主题；高密度、克制。

### 技术线索（待核验）

下面这些是从早期调研里抓取的，**没有重新核实**，issue 编号与产品能力随时间会变。只当作要不要做 spike 的线索。

- **现成的图库只解决单一图的编辑与布局**（React Flow、G6、Cytoscape 一类）；这里要的是语义缩放、拓扑变换的动画、多视图协调，所以领域的投影引擎（关系种类、消息树到上下文链、压缩节点、表示的层级）必须自研。
- **自动布局不能当空间语义的来源**：布局引擎的交互式布局只是「尽量少改已有布局」。建议：领域图决定自己的层、道与锚点，布局引擎只解局部的排布与走线，得到世界坐标，这样布局引擎重排失败不会破坏语义轴。
- **不跳变靠投影契约，不靠布局引擎**：预生成一系列逐级细化的表示，缩放时选层，要求相邻两层的父子对应：新出现的有出生锚点，被聚合的有死亡锚点；边也一样，聚合边是细边束的祖先，不对两套无关的线路做交叉淡入。
- **动画的价值**：一项综述指出没有一致证据说明「已有节点尽量不动」总能改善理解。所以连续动画的更强理由是解释表示的转换本身（这个任务展开成哪些步骤，这些消息怎样收束），用运动表达来处，而不是为了保持心理地图。
- **一个可 spike 的商业布局库**：区分固定与增量元素的增量布局，把一个节点固定在某个角的锚定，只布局指定子图，原生的细节层级。要测：表示逐级细化的转场、开源布局引擎在硬的领域锚点下能承担多少、商业库的增量与锚定能省掉多少自研。
- **性能要先测再选**：复杂边下几十个节点就可能出问题，所以要对同一批固定数据与设备做基准，不是现在迁移；Canvas 与 WebGL 留作逃生口。
- **前端工具链**：TypeScript、Node.js、Electron、React、Vite 在早期验证过可构建、可打包。Kernel 现在是 Rust，经本地套接字的会话，前端用什么还没定。

状态：原则与取向是方向；技术线索是待核验。

## 工具的哲学

工具的作用主要是让框架知道模型做了什么。若只是为了模型方便，完全可以介绍怎么用命令行里的库。这里有一个可能的矛盾：模型需要足够正交的工具，而框架需要足够的方法去捕获模型做的事情。

一个可能的解法是容器加网络控制：效果不靠工具捕获，工作区前后两棵 Tree、出站代理的记录都在 Journal 里，再让模型查看容器的差异、输出结构化的字段。没说清的是**意图**：模型绕过工具直接改文件时，框架仍然知道改了什么，却读不出它想做什么。

缺一个场景：模型绕过工具直接改文件，框架怎样还原意图。

状态：方向。
