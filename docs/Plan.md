# 开发规划

全文是打算，按待定读：设计以各部分为准，这里只说 croon-app 在哪个阶段、做完了什么、下一步做什么、怎样算做完。跨部分的实现选择见 croon:docs/Kernel/Engineering.md「选择」，绑某一部分的见各部分的「实现」。各阶段只收选定场景需要解决的问题，必要的代码验证可以穿插进行，不要求全部设计完成才开始实现。

## 范围

现在只做本地单租户：一台机器，一个系统，一个根。云上多租户暂不做，接口见 croon:docs/Kernel/README.md「待定」里的「云上多租户」：每个操作带系统 ID，存储按系统分开。

croon-app 拥有模型适配、Directory 与 Docker 文件执行、Library 与 Application；Kernel 的通用契约和 Lang0 的求值器由上游仓库拥有。本仓库只写应用侧的决定，Kernel 与 lang0 的语义见各自的权威文档。

## 现在

生命周期的 0。运行闭环的一次性版本已经接上真的外部执行：根经宿主装起系统，交一个任务给 W0，取回结果写进新目录；中断后同一个 Kernel 目录重跑即恢复。已完成：

- **宿主装配**：host.config 装起 Kernel、Lang0、模型与 Docker 文件执行，app 自己的 root Definition，一次性客户端 `croon-app run`，见 Host/README.md。端到端由 host 的 `host`、`delegation` 测试验收，用真 Docker 与脚本化或回放的模型。
- **模型**：OpenAI Chat Completions 适配器；录制与回放按逻辑行动领用；失败按谁能修好分成 use 与宿主故障，见 Model/README.md。真 Provider 由 `smoke` 冒烟。
- **工作区**：私有工作区收拢快照、派生与采用；并入按目录三方合并，不看提交状态，不在 /work 里生成提交，结果确定，见 Library/Runtime.md「工作区」。
- **恢复**：每个提交点前后停下，重跑结果与记录序列相同（`recovery`）；exec 在途时 SIGKILL，旧 attempt 退役、新 attempt 重做（`kill`）；宿主故障时客户端带原因退出，修好后重跑重开接着走（`failure`）。
- **场景**：Delegate 场景归本仓库，root 用 host.root，预期由 CPython 独立求出并逐条核对，见 Library/Scenarios/Delegate.md。
- **运行中构造与交办**：W0 有三个管理器工具。`look` 只读 Library 目录，不起 exec：不给名字是 README 与各模块的一句话，给模块名是它的公开面（宿主经 `definition.infer` 的模块目录问法，从 `lang0::surface` 推出），`source=True` 是源码。`make` 收一份源码或工作区里的一个路径，经 `definition.infer`、pack、construct 构造，载入工具表，从下一轮起模型以它的名字直接调用，输入按它 main 的参数写，工作区的 `snapshot` 由工具填。清单里的 Agent（现在是 s）在启动时同样载入。`merge` 并入交回的目录。调用即实例化、经 Notify 收取结果；接线按目标声明的名字，从愿意交出的（W0 现在是 engine、exec）里取，是否恰好覆盖由 Kernel 检查；工作区只在目标的 in 或结束值里有 `snapshot` 时才介入，纯计算的主体不拿工作区。纯计算、只用模型、改文件三种主体与接线错误由 `construct`、`shapes`、`agent` 验收，预置的 s 走同一条路径（`delegation`、Delegate 场景）。W0 自带的只有管理器：Library 目录（`library/` 与 `tools.json`）作为目录 Bundle 交给它，它读清单载入函数工具包（现在是 files）与 Agent；根只构造 W0。函数工具包由宿主生成的 `library.tools` 列出。还没有名字空间：载入的工具表是 W0 里的一个列表；没有「装」，清单是启动时读一次，Library 目录也不留存。推导的设计见 Host/README.md「构造的推导」。

**已落地的运行入口**：`croon-app run` 开始，`resume` 续做（关机、被杀、宿主故障之后都是这一条，任务与目录取自 Journal，录像接着追加），`exec` 直接运行一份源码，不经 W0。镜像是 `croon-work:2`（alpine、git、python3、pytest）。

**尚未落地**：没有上手路径，README 不写怎样建任务镜像、写 host.config、跑 `croon-app run`，`config/` 下也没有模板；需要真 Docker 的测试都标了 ignore，没有统一的跑法与前提说明，其中 `smoke` 会调用真模型。root entry 只在进程内，没有 socket 与持续对话。Library 目录不留存、结果不写回调用方的目录：设计已定，见第 2 步。

**实测证据**（做法、判据与记录格式见 Experiments.md，任务与检查器在 experiments/）：

- 14 个小任务，纯计算、改文件、用模型三类各几个；10 个调整用，4 个留出，调整时不跑。每个任务跑一两次，模型是 gpt-6-astra，一次也有用 gpt-6.1-sol 的批。检查器由实验方写，用 `croon-app exec` 在检验方自己的输入上把造出来的源码再跑一遍，识破「写死答案」；改文件的任务用隐藏测试。
- **结果**：最后一版代码上，调整用的 10 个全部通过；留出的 4 个也全部通过。**一个任务一两次的样本只说明路径走得通，不是通过率，也不能推到别的任务与别的模型。**
- **实验找到的问题，没有一个出在模型上**，每一个都是系统自己的缺口，修的是系统：
  - 快照还原成目录时子目录权限太紧，容器读不了自己的输入，`cp` 失败，`resume` 也救不回来。修在 Directory，权限由它规定，见 Directory/README.md。
  - 模型服务偶发 503，W0 以失败结束。Library 的 `generate` 现在重试偶发失败，见 Library/Runtime.md「模型调用」。
  - 构造不过时，Lang0 的报错不说用什么代替（`.lower`、`set`、带类型的局部赋值），模型绕远路。现在会说，`make` 的失败次数在受影响的任务上从 7 次降到 2 次。
  - 测试台自己的错：参考答案数错、检查器认不得 `generate`、对 `make(path=…)` 看不到源码。这些记在 Experiments.md。
- **没有证据的**：任务都很小，调整用的已经全部通过，所以现有任务不能再区分好坏。长任务、多主体协作、更难的 Lang0 写法、别的模型都没有测。exec 开销、内容库增长、恢复重放耗时与 tombstone 积累仍没有系统测量。

## 下一步

前一阶段的四步已经走完一轮：W0 只带管理器、运行中构造与交办（做了，`construct`、`shapes`、`agent` 验收，逐提交点与 exec 在途 SIGKILL 的恢复由 `recovery`、`kill` 验收）；管理器的看与造（做了）；真实模型的实验闭环（做了，见上面的「实测证据」）；按失败证据改一项再复测（做了三项，见同处）。上手路径也补上了：README、`config/` 下的模板、实验的说明。

现在的取舍：**不再在这里加难度、也不做大的长程工程**，先把已经做到的公开出来，由外部的反馈决定往哪走。下面是各项的状态与触发条件，不是承诺的顺序。

**新用户走查，三轮**（每轮一个没有项目上下文的子代理，只凭 README 与文档，用 gpt-6.1-sol 跑真实任务；前两轮开放式找问题，第三轮逐条核对上一轮的问题是否真的修好）：

- **第一轮**：构建、镜像、`run`、`resume`、`exec` 全部成功，没有阻塞；8 处麻烦、4 条建议。主要三类：文档把设计写成了现状（采用与 diff、Library 路径）、每开一个新任务要复制整份配置改四项、运行时没有进度。
- **第二轮**（改了文档、加了会话、进度、配置默认值之后）：第一轮的问题基本消失，但新功能带来了新的：裸 `resume` 先要 `--out`、重复会话报「录像已存在」、拼错名字留下一个空会话并污染列表、进度不带命令文本且 `resume` 会重放旧步骤。
- **第三轮**（修了上面之后，逐条核对）：七条里重复会话、不存在的会话、无配置的 `run` 三条解决；进度（命令可见、`resume` 不再重放、历史摘要）算解决，计时在「接着上次做」那一行重新开始是有意的；还剩下面几处，**没有再修，记在这里**。

**开源时已知、没有修的问题**（第三轮报告里的，都不阻塞，都是真的）：

- 没有配置文件时，`resume` 不带参数**列不出已有的会话**，`resume` 一个不存在的名字也先报缺配置而不是「找不到会话」。原因：读配置发生在查会话之前；会话本来是只读查询，不该依赖配置。应当先查会话、后读配置，`run` 对已有会话同理。
- 列出会话时，列表打在标准错误上，**退出码是 2**，脚本会把一次成功的查询当成错误。应当打在标准输出、退出 0。
- 会话列表只有名字，没有「是否结束」「任务是什么」「什么时候」。
- 进度里的耗时在 `resume` 的「接着上次做」那一行之后重新计时，所以看不出一个会话总共用了多久。
- 命令行的几种状态组合（有没有配置 × 有没有会话 × 会话开没开始 × 是不是查询）是靠走查一个个撞出来的，没有一张表和对应的命令行测试。每多一个入口就多一组组合，三轮走查里**相当一部分问题是上一轮的修复自己带来的**。下一次动命令行之前，先把这张表写出来、每格一个不需要 Docker 的测试。
- 只测了一个中断时点（成功的命令之后被杀）。关机、断网、正在执行容器命令时被杀，由 `recovery`、`kill` 覆盖，但没有让一个陌生使用者从头做过。
- 镜像从零构建、`docker pull` 没有被走查验证（本机已有，按任务要求没重建）；第一轮用户拉 `python:3.12-slim` 用了 5 分钟。
- 输入目录不是 git 仓库时的行为验证过；是真实 git 仓库（含 `.git`、忽略文件、大仓库、二进制）没有验证。

这些在表里的位置见下面的取舍表，不再单独占一个清单。

| 事项 | 状态 | 什么时候做 |
|---|---|---|
| 更难的实验任务（多文件项目、两个主体协作、Lang0 没有的能力、含歧义的需求） | 没做 | 调整用的任务继续全部通过、不再能区分好坏时；它需要开发资源，现在没有 |
| 留存：Library 目录在磁盘上、`装`、`apply`、任务目录写回 | 设计定了（Library/Packages.md、Host/README.md「结果与采用」），没写代码 | 有人要把造出来的东西带到下一次运行时。README 里已经写明现在不留存 |
| 名字空间 | 载入的工具表是 W0 里的一个列表 | 运行中有 Reference 到达的时候（持续对话） |
| 目录字段由 Signature 声明 | 上游待定（croon:docs/Kernel/Value.md） | 有一个 Definition 要收两份目录时；之前按字段名 `snapshot` 认 |
| 持续对话、软硬打断 | 没做 | 任务需要运行中追加输入或干预时 |
| Kernel 听不到「启动失败已清理」 | 写进了上游待定（croon:docs/Kernel/Reference.md） | 出现第二个场景（镜像缺失、Docker 临时不可用）时 |
| `croon-app init`：交互式建用户空间、问模型地址与密钥、检查 docker 与镜像 | 没做 | 有外部使用者说「第一次配置太麻烦」且最小配置（见下）仍不够时。**现在不做的理由**：走查里没有人卡在这里，卡的是「每个新任务要换四项」与「字段多」，那两样做了 |
| 用户空间 `~/.croon/`：多份模型服务（`providers.json`）、用户的包目录 | 没做 | 有人要在几个模型服务间切换，或要把造出来的主体带到下一次运行时。后者与「留存」是同一件事，不另做一次 |
| 项目级目录（像 `.claude/` 那样放项目自己的工具清单与说明） | 没做 | 有项目要带自己的工具清单时 |
| 模型配置放进模型自己的 crate 所有（Model 读自己的文件，宿主只引用名字）；`directory` 的配置形状回到 Directory 的 crate | 没做 | 想让 Model 与 Directory 能脱离宿主单独使用时。**现在不做的理由**：用户看不到，只是内部更整洁；`directory` 配置的形状现在写在 `host.config` 里，违反「block 在用它的最低一层」，已知 |
| 运行进度的详细日志、token 与费用统计、预算上限 | 只做了进度行（见下） | 有人要控制费用时 |
| 先查会话、后读配置；列会话打在标准输出并退出 0 | 现在没配置时列不出会话，列出来也退出 2 | 第一个有人在没配置的机器上或在脚本里查会话时。改动很小，是已知缺口，不是设计 |
| 命令行状态组合的表与对应的测试 | 没做 | 下一次动命令行之前。三轮走查里不少问题是上一轮修复自己带来的，靠走查一个个撞太贵 |
| 会话列表里带上「是否已结束、任务是什么、什么时候」 | 现在只列名字 | 有人记不住哪个会话是哪个任务时。这需要读每个会话的 Journal，不是只看目录 |
| 把总结里的容器路径（`/work/a.py`）换成宿主上的真实路径；把 diff 作为一等输出 | 没做 | 有了「写回」之后一并做，它们是同一个出口 |
| 联网、Charter 版制造 | 依赖上游 | 见「以后的方向」 |

**为什么「用户空间」现在不做。** 同类工具（pi 的 `~/.pi`、Claude Code 的 `~/.claude`、Codex 的 `~/.codex`）都有，里面是四类东西：配置、凭据、跨项目的内容（skills、AGENTS.md、扩展）、运行状态（会话、历史、日志）。我们这四类都有，只是散落：配置在用户随便放的 `host.json`，凭据在仓库的 `config/`，内容（Library）编进二进制，运行状态在 `--config` 里写的 `kernel` 目录。把它们收到一个约定的位置，是对的方向，但它依赖「留存」这件事先做出来：现在没有跨运行的内容要放，造一个空的目录约定没有意义。所以顺序是：先做留存，用户空间随它一起出现。


## 制造闭环

一个主体在运行中造出另一个主体，交办一件事并审阅结果；有文件产物时再按工作区规则并入。它检验「Definition 与 Charter 是数据」的设计，以及授权只收窄、修正权独立、可追溯在应用组合中的落实。分三步，前一步不通不做后一步：

1. **Cognition 版**：W0 经工具构造一份 Cognition Definition，实例化、交办并收取结果。代码依赖取自自己 Definition 的完整 Bundle，模型碰不到 ID。不依赖 Kernel 的新功能；当前证据与限制见「现在」。
2. **模板与说明**：Library 的包里提供 Charter 生成函数（N 个同样的 Seat、审计者、熔断者）与可运行的例子，经管理器给出，模型选模板、填参数，不手写整份 JSON。
3. **Charter 版**：同样的流程，造的是 Charter。依赖 Kernel 的构造检查（pin 的 Definition 满足 Seat）、终止闭环与对 Collective 的 Correct，见 croon:docs/Kernel/Definition/README.md「检查」与 croon:docs/Kernel/Instance.md「待定」。Cognition 的实验不等待这些工作。

验收分为机制与使用两组。

**机制验收**：

- 不同形状的主体可构造和运行；源码错误带位置与原因返回，输入与接线错误能被拒绝；结果及依赖经 Notify 正确返回。
- 制造路径覆盖 infer、pack、construct、instantiate 与结果收取的每个提交窗口，中断后重跑结果相同；执行在途时的进程中断也要覆盖。两者都已验证（`recovery`、`kill` 里造出来的主体各一条）。
- 委托深度按 Library/Runtime.md「不建议委托超过两层」的默认接线写进场景。
- Charter 阶段另验构造、终止与 Correct，并用检查器查出「审计者被执行者控制」等图性质。

**使用验收**：在固定模型、说明、任务和修复预算下，记录构造、运行与任务验收各阶段的结果。真实模型须能根据任务写出主体、理解反馈并修复，最终通过独立判据；成功率、修复成本与耗时由实验给出。修复预算用尽时保留完整尝试，分析失败原因；是否改用模板或 Library 生成，由对照实验决定。

制造闭环之后，「跑通」以下面两条为准；Application（收什么见 Library/Presets.md「Application」），如个人生活管理，排在它们之后。

- **一天内复刻**：市面上任何一个 Agent 框架出现，不到一天就能用 Croon 把它的核心逻辑写出来，并且同样用 Croon 写出它的测试、跑完。复刻的是核心逻辑，不是源码。复刻不出的，就是 croon:docs/Kernel/README.md「运作方式」的缺口。
- **复刻者**：造一个专门制造或复刻别的 Agent 的主体，它把做过的经验存下来，拿到一个 Agent 的源码或文档架构，就能批量复刻。

复刻的对照：别的框架回答过的问题，Croon 都要有一个落点。先做 DSH（DeepSeek Harness）：它用到的技术各回答什么问题，Croon 用什么组合回答；结果进 Research，缺口进 croon:docs/Kernel/README.md「运作方式」。

## 测试

| 验证方式 | 能证明什么 |
|---|---|
| 脚本化模型与真实执行 | 指定路径的机制、交付、接线和结果处理成立 |
| 录制与回放 | 固定请求与结果下可重复运行 |
| 故障注入、进程中断 | 被覆盖路径的恢复行为成立 |
| 真实模型与固定检查器 | 在给定任务和条件下的实际完成能力 |

- **场景**：Library 的场景预期在 Library/Scenarios/，测试拿真的 Kernel 与 Lang0、假的模型与文件执行驱动，逐提交点与逐 provider Atom 在途崩溃比对 Journal；预期由 CPython 独立求出并核对。
- **端到端**：host 中需要真 Docker 的集成测试标了 ignore，依赖本机的 croon-work:2 与 python:3.12-slim；ignore 表示默认跳过，不表示未经运行。模型通常用脚本化或回放的，录像只在临时目录。`smoke` 调用真模型，会产生费用，目前主要断言运行完成、结果目录存在及录像不含凭据，不替代任务正确性检查。
- **恢复覆盖**：`recovery` 覆盖预置交办与运行中造出来的主体两条路径的逐提交点中断；`kill` 覆盖 exec 在途 SIGKILL，同样两条路径；`failure` 覆盖宿主故障后修好重跑。跨 Kernel 目录比结果与记录序列，同一目录内逐字比。`construct` 验证构造后以空录像重跑，`agent` 与 `shapes` 验证文件型与别的形状的主体完成与跨系统回放。清单（`home`）在装配时检查，不需要 Docker。
- **实验记录**：机制与格式见 Experiments.md。保存任务、判据、模型与说明、代码版本、修复预算、源码尝试及每轮失败的 kind 与 message。记录失败阶段、修复次数、检查结果、模型耗时与用量、exec 次数与耗时；较长任务和持续运行实验追加内容库大小、恢复时间、tombstone 数量。任务未完成、宿主故障、检查器故障分开统计。
- **独立验收**：检查器由实验方固定，被测主体不能修改；检查实际结果的正确性，不只看退出码，必要时加超时与资源限额。失败尝试也保留记录。

## 以后的方向

按需求或实测结果启动，不作为近期实验的统一前置条件：

- **持续对话**：任务需要运行中追加输入、反问或干预时，推进经 socket 的 root entry、软打断与硬打断；场景见 croon:docs/Kernel/README.md「W0 持续对话」。
- **运行成本**：测到对应成本妨碍目标任务时再优化。Checkpoint 降低重放计算成本，存储去重降低内容库增长，执行提供者与调度优化降低调用开销和等待成本，分别验收；tombstone 的处理须维持 Directory 的退役保证。
- **Charter**：开始组织型实验前补齐「制造闭环」Charter 版所依赖的正确性缺口。
- **实验台做成 Definition**：任务协议、评价与记录方法稳定后，把已有实验能力组合成专门的 Definition，跟它说话就能提实验、看结果；复用通用交办与固定检查器，被测主体不自评。
- **场景同步工具**：随实际改动减少 Interface、工具说明等派生数据的手工维护；关键行为预期保留独立来源与明确断言，不由被测实现自动生成。不作为实验的前置大项目。
- 联网：可用性要它。做法在 croon:docs/Kernel/Reference.md「通道」与待定；现在不联网。
- 历史管理：执行恢复依赖 Journal 的分叉待定。
- **语言摩擦对照**：当近期实验反复撞到 Lang0 的表达限制时，为同一场景分别写普通 Python 与 Lang0，逐处说明差异及其原因，检查是否存在未报告的语义变化。模型完成能力的量化按 Experiments.md 与「测试」推进。
- Provider 的管理面：KV Cache 的管理、推理的控制面。前缀复用现在只能在基础设施一侧做，经 HTTP 够不到；线索见 croon:docs/Kernel/Port.md 的待定。排在靠后。
- 生态入口：经 MCP、A2A 接别的框架与客户端，Croon 作调用方或被调用方。依赖联网与系统边界，排在阶段 2、3；见 croon:docs/Kernel/README.md「待定」里的「系统边界」与 croon:docs/Kernel/Plugin.md「待定」。
- 独立软件交付：是否把一份 Application 连同它的 Definition、资源、界面与 Kernel 运行时一起打包，安装后即可使用；运行权利与凭据由部署时的根接入。内嵌运行时、容器依赖、安装与升级，等首个 Application 的场景明确再定。 打包时 App 的包与用户的包要分层，见 Library/Packages.md「目录与留存」。
