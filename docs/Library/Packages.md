# 包与家目录

Library 是一组包；用户有一个家目录，装着用户自己的包、工具清单与技能。管理器是看、装、载这三个操作，载入的东西就是工具。本文写包是什么、家目录在哪、属于谁、管理器管什么。

## 包

包是一个目录，里面是 Lang0 模块，带一份手写的 README.md，说明它是什么、怎样用。所有包并排放在同一个目录下，那个目录就是 import 的起点：`import library.files` 找名为 library 的包里的 files.py。装载的语义见 croon-lang0:docs/README.md「模块」。

- **主体也是包。** 带入口模块 `main.py`、其中有 `main` 的包就是一个可以实例化的主体。App 自带的主体（W0、s）、用户装的、运行中造出来的，都是同一种东西：一个目录，一个入口。包名由造它的一方起；运行中造的，名字是模型自己起的，满足 README.md「模型看到的名字极简」。
- **公开面**：名字以下划线开头的不公开，不进索引。
- **索引**：宿主从源码推出，规则与推 Interface、`croon.tool` 的说明相同：签名、类型、docstring 与其中的 `Args:`，Port、TypedDict 与 Schema 一并收。索引是源码的派生物，从不落盘：导入家目录时由宿主为每个包推出，运行中新装的包经宿主的推导 Port 现推，见 ../Host/README.md「构造的推导」。所以它与代码永远对得上，没有人能把它改旧。
- **按层展开**：一句话（包的 docstring 首行）、README、模块索引、某一项的签名与说明、源码。模型按需要往下读，每一层作为工具结果进入历史；常驻的只有每个包一行。
- **例子**是包里可以直接运行的主体。测试负责构造并运行它们，例子因此不会过期；模型可以照抄它的源码，也可以直接载入它。

## 两层

包分两层，按来处分：

| 层 | 收什么 | 在哪 | 谁改 |
|---|---|---|---|
| App 的包 | 核心库、生成模块、W0、s | 编进二进制，随 App 的版本走 | 只读；App 升级时一起换 |
| 用户的包 | 用户与它的手装的、造的 | 磁盘上的家目录 | 用户与它的手 |

宿主运行时按包名把两层合成一份交给手，同名就报错，用户的包盖不掉 App 的包。

App 的包不复制进家目录：生成模块依赖当前宿主的 Port 规格，W0 的代码要与宿主的 root Definition 对得上，留在家目录里的旧副本会在 App 升级后对不上。这与包管理器把系统包与用户包分开是同一个理由。

**生成模块**属于 App 的核心库，由宿主生成，与手写的模块一起固定进目录 Bundle，重放不随宿主构建改变类型：library.kernel 只提供 KernelPort 的 Port spec 与 Outcome；library.model 的 Generate 来自 model.generate；library.directory 的 Exec 来自 directory.exec；library.infer 的 Infer 来自 definition.infer；library.tools 列出诞生时可载入的函数工具包，见 Runtime.md「工具」。它们的源码不进 Git，由本仓库的生成器产生。

## 家目录

家目录是磁盘上的一个目录，路径写在宿主配置里。里面是用户的包、工具清单 `tools.json`（形状是 `home.tools`）与技能。第一次运行时，宿主把 App 的默认清单复制进去。

- **属于用户，不属于手。** 装的包、造的主体、改过的清单要在手结束之后还在，也要让用户的别的手、下一次运行看得见，所以放在用户那一层，不放在某一个手里。手经接线拿到读与提交的权利，见 Presets.md「预置给谁」。
- **为什么在磁盘上，不在系统里由保管者持有**：家目录属于用户，用户在系统外；导入与写回是根在系统外的事，与仓库同一个位置，见 ../Host/README.md「装配」。用户能用编辑器看、改，用 git 管自己的包与技能。保管者能给的历史与共享，这里由 git 与写回时的三方合并给出。
- **在系统里是一个工作区**：宿主导入时把两层合成一份目录 Bundle 交给手，手的「装」「载」移动它的当前位置，规则见 Runtime.md「工作区」。结束时宿主只把用户那一层按三方合并写回磁盘，见 ../Host/README.md「结果与采用」。
- **与仓库分开**：它与任务给的目录是两个工作区，当前位置各自移动；交回结果时不带家目录。

## 管理器

管理器是 Library 里的函数，不是 Definition，也没有自己的身份。它有三个操作，都作为手的工具：

| 操作 | 做什么 |
|---|---|
| 看 | 本地有什么、怎么用：按名字往下展开。不给名字是概览，给包名是 README 与模块列表，给模块名是它的索引，给一项是它的签名与说明，最后才是源码。只读家目录，不起 exec |
| 装 | 把一个包放进家目录：来源是模型写的源码、任务目录里的一个目录，或以后的联网下载。派生新的目录 Bundle 再采用；能 diff，能回滚。新包的索引经推导 Port 现推 |
| 载 | 把一个包里的主体或函数接好线，变成工具表的一项，并记进 tools.json，下次运行还在；见 Runtime.md「工具」 |

- **造一个主体就是装加载**：模型写源码，装成一个包，再载入，它就成了手的一个工具，以后的运行也在。不另设「造」的概念。
- **模块也能装**：家目录是用户自己的地方，手往里写，像往用户目录里装软件；装上的只有被载入或被 import 时才生效，影响只到用户自己以后的运行。
- **人与手是同一组操作**：人经客户端做的看、装、载与手经工具做的落在同一份实现上；人也可以直接改磁盘上的家目录，下一次运行导入时生效。

## 待定

- 联网下载包：依赖 croon:docs/Kernel/README.md「待定」里的「系统边界」。内容寻址的哈希就是锁定。第三方的包没有环境权利，只能用接给它的 Reference，所以风险只有两处：接给它什么，以及它的输出对模型的影响；后者在作者与使用者不再是同一个人时才出现。「装」的来源留成可以扩展的形状，接上联网时不改它的用法。没有场景。
- 多库组合：不同的包同时载入时，要不要识别组合、给结合使用的教程；识别到什么程度。没有场景。
- 索引的推导需要 croon-lang0 的一个公开 API：枚举一个模块的顶层公开定义并逐个推导，含 Port、TypedDict 与 Schema。这是上游的缺口，见 croon-lang0:docs/README.md「待定」里的「模块公开面的推导」。
- 每一层展开给多少内容：由实验定，见 ../Plan.md「下一步」。
