# 开发规划

全文是打算，按待定读：设计以各部分为准，这里只说 croon-app 在哪个阶段、做完了什么、下一步做什么、怎样算做完。跨部分的实现选择见 croon:docs/Kernel/Engineering.md「选择」，绑某一部分的见各部分的「实现」。各阶段只收选定场景需要解决的问题，必要的代码验证可以穿插进行，不要求全部设计完成才开始实现。

## 范围

第一版只做本地单租户：一台机器，一个系统，一个根。云上多租户第一版不做，接口见 croon:docs/Kernel/README.md「待定」里的「云上多租户」：每个操作带系统 ID，存储按系统分开。

croon-app 拥有模型适配、Directory 与 Docker 文件执行、Library 与 Application；Kernel 的通用契约和 Lang0 的求值器由上游仓库拥有。本仓库只写应用侧的决定，Kernel 与 lang0 的语义见各自的权威文档。

## 生命周期

| 阶段 | 完成判据 | 瓶颈 | 做什么 |
|---|---|---|---|
| 0 设计验证 | 「现在」一节做完的几样 | 设计没被实现撞过 | 不拉人；主仓库全开源；写设计文但不发流量；公开验收标准 |
| 1 最小闭环 | 运行闭环（一次性版本已完成，见「现在」）与「制造闭环」的判据 | 项目死亡率最高 | 不拉人；聚焦闭环与实测 |
| 2 外部验证 | 别人能按 README 跑通 | 从「我能跑」到「别人能跑」 | 找 3 到 5 个验证者；修文档与环境；定扩展协议 |
| 3 第一批贡献 | 有人开始写扩展 | 贡献入口不清楚 | 按 croon:docs/Kernel/README.md「制度机」的边界开官方扩展仓库；切边界清楚的活；定许可证；发生态内容；写扩展的设计手册 |
| 4 生态治理 | 到时再定 | 来的人改变项目性质：社区在改项目 | 写治理文档，划出不可妥协的保证与边界 |
| 5 商业化 | 到时再定 | 全开源下怎么持续：规模起来 | Kernel 永远开源；价值在扩展、托管、支持 |

时机：

- **拉人**：阶段 1 结束前不拉；第一个不是贡献者，是能一起撞实现的人。
- **流量**：跟着阶段走，跑通那天才发第一篇带代码的。
- **扩展仓库**：核心契约和 Bundle/交付形状稳定后再开；提前开会把未收敛的边界交给扩展。
- **公开**：三个仓库都还没公开。公开前补上手路径与许可证，各仓库扫一遍历史里的凭据；公开时只推 main，不用 --all、--mirror、--tags，旧历史留在仓库之外。

## 现在

生命周期的 0。运行闭环的一次性版本已经接上真的外部执行：根经宿主装起系统，交一个任务给 W0，取回结果写进新目录；中断后同一个 Kernel 目录重跑即恢复。已完成：

- **宿主装配**：host.config 装起 Kernel、Lang0、模型与 Docker 文件执行，app 自己的 root Definition，一次性客户端 `croon-app run`，见 Host/README.md。端到端由 host 的 `host`、`delegation` 测试验收，用真 Docker 与脚本化或回放的模型。
- **模型**：OpenAI Chat Completions 适配器；录制与回放按逻辑行动领用；失败按谁能修好分成 use 与宿主故障，见 Model/README.md。真 Provider 由 `smoke` 冒烟。
- **工作区**：私有工作区收拢快照、派生与采用；并入按目录三方合并，不看提交状态，不在 /work 里生成提交，结果确定，见 Library/Runtime.md「工作区」。
- **恢复**：每个提交点前后停下，重跑结果与记录序列相同（`recovery`）；exec 在途时 SIGKILL，旧 attempt 退役、新 attempt 重做（`kill`）；宿主故障时客户端带原因退出，修好后重跑重开接着走（`failure`）。
- **场景**：Delegate 场景归本仓库，root 用 host.root，预期由 CPython 独立求出并逐条核对，见 Library/Scenarios/Delegate.md。
- **运行中构造与交办**：W0 的 `delegate` 工具收一份源码、工作区里的一个路径，或一个已有的名字；经 `definition.infer`、pack、construct 构造，实例化，经 Notify 收取结果。接线按目标声明的名字，从交办一方愿意交出的（W0 现在是 engine、exec）里取，是否恰好覆盖由 Kernel 检查；工作区只在目标的 in 或结束值里有 `snapshot` 时才介入，纯计算的主体不拿工作区。纯计算、只用模型、改文件三种主体与两种接线错误由 `construct`、`shapes`、`agent` 验收，预置的 s 走同一条路径（`delegation`、Delegate 场景）。还没有名字空间、家目录与载入：预置的 s 仍由根构造、经 `worker` 输入传给 W0，工具表是固定的。推导的设计见 Host/README.md「构造的推导」。

**尚未落地**：没有上手路径，README 不写怎样建任务镜像、写 host.config、跑 `croon-app run`，`config/` 下也没有模板；需要真 Docker 的测试都标了 ignore，没有统一的跑法与前提说明，其中 `smoke` 会调用真模型。root entry 只在进程内，没有 socket 与持续对话；结果只写进新目录，写回用户仓库仍待定。

**尚无实测证据**：真实模型编写 Definition 的构造成功率、修复轮数、运行成功率和任务完成率。现有构造测试使用预写的错误与修正版源码，不代表模型能根据诊断自行修复。新制造路径尚未覆盖逐提交点中断与恢复；已有恢复测试覆盖的路径见「测试」。exec 开销、内容库增长、恢复重放耗时与 tombstone 积累尚未系统测量，是否构成瓶颈由实验判断。

**摸底**（一次，不作测量；那时 W0 还带着预置的 S 与 `construct_agent`）：gpt-6-astra 接到「造一个 Agent 交办给它修好 a.py」，猜了 library.coding、library.agent、library.llm 等七次构造，能过构造的只有不用任何能力的空壳，运行时失败后转用预置的 delegate 交给 S 完成；任务镜像里没有 Python，S 改用 awk 自检。模型读不到 Library 有什么，是先于形状的阻碍；有低负载的预置工具时，模型会绕开构造。

## 下一步

近期按下面四步推进，前一步的证据决定后一步的范围。第 1 步是「制造闭环」Cognition 版的机制验收，第 2 步是第一次测量之前必须有的基线，第 3、4 步是使用验收。其余工作按「以后的方向」里的条件启动。设计见 Library/Packages.md、Library/Runtime.md「名字空间」「工具」「交办」与 Library/Organization.md「做法怎样变」；下面只写判据。

1. **W0 的最小形状与通用交办**：W0 是用户的手，自带的只有管理器；改代码的子代理 S 与文件工具成为 Library 里的包，由默认清单载入；交办不依赖 S 的形状。已做：通用运行、构造并入交办、工作区分层，见「现在」；没做：名字空间、家目录、清单与载入、`worker` 去掉，以及制造路径的逐提交点恢复。
   - 运行与工作区分层：通用运行按目标的 Interface 给输入、按声明的名字从名字空间附带 Port、经 Notify 收回结束值；只有目标收 `snapshot` 才交付快照，结束值带 `snapshot` 才 diff、等待并入。不收目录的主体既不拿到工作区，也不多起一次 exec。
   - 接线只按声明的名字取，是否恰好覆盖、规格是否相同由 Kernel 检查，Library 不另写一份。敏感能力要不要显式点名，见 Library/Runtime.md 待定，第一版不做。
   - 构造并入实例化：实例化收源码、路径或包，构造失败就是实例化失败。名字空间取代 `agents` 表与 `describe_agent`。
   - S 与造出来的主体走同一条交办路径：Delegate 场景的 CPython 核对与逐提交点、逐 Atom 在途的崩溃测试于是覆盖通用路径；`host::run` 不再构造 S，W0 不再收 `worker`。
   - 判据：纯计算（无目录、无模型）、只用模型、改文件三种主体都能构造、交办、收回结果；接不上与规格不同的接线以可读的错误回到模型；制造路径（infer、pack、construct、instantiate、收取）逐提交点中断后重跑结果相同，造出来的主体 exec 在途时 SIGKILL 能恢复。
2. **包与管理器**：家目录、索引、看、装、载。它是第 3 步的基线。
   - 家目录第一版作为目录 Bundle 交给 W0，结束时不写回；包带 README 与宿主从源码推出的索引，按层展开。索引的推导要 croon-lang0 补公开 API，这是上游的前置。
   - 第一次测量之前，模型要能读到 Library 有什么、怎样写一个主体：`main` 的签名就是 Interface，能 import 哪些模块，能附带哪些 Port，工作区的约定。没讲的，测到的只是没告诉模型。每层展开给多少由实验定。
   - 任务镜像要带上任务用到的运行时。
   - 判据：不看源码仓库，模型只靠管理器能说出某个包怎样用，并据此写出能过构造的主体；包里的例子由测试构造并运行。
3. **建立最小真实模型实验闭环**：从任务与允许使用的能力出发，由真实模型写源码、据诊断修复、构造、运行，最后由独立的固定检查器验收。先选少量不同类型的任务：纯计算、文件修改并通过固定测试、需要模型或其他已有能力的主体。先验证记录与评价方法，再扩大任务集和重复次数；少量任务的成绩不作总体成功率。每次用 record 模式保留模型往来，记录要求见「测试」。判据是每次尝试都能得到可核查的验收结果，失败能定位到阶段。
   - 测制造的任务不载入预置的子代理，否则测到的是绕开构造。
   - 验收不凭 W0 的转述：产出文件的任务查物化后的结果目录；产出值的任务把造出来的 Definition 从内容库取出，在实验方自己的输入上另行实例化，比较结束值。
   - 记录取自录像与 Journal：录像里有每轮工具调用、失败的 kind 与 message，Journal 里有各阶段的提交与 exec；Library 不为实验另加埋点。
4. **根据实验结果改一项，再复测**：按失败证据选择报错文本、工具说明与示例、包的 README 与索引、Lang0 子集、Library、机制、模型或运行成本中的一项。一次只改一个因素，在原任务和未参与调优的任务上比较收益及退步；重复次数随方差增加。判据是能说明改动针对哪类失败、证据来自哪些任务，以及改动是否有效。

上手路径随第 3 步补齐，作为实验可复现的交付物：README 写建镜像（含换源参数）、host.config 与 `croon-app run`，提交 `config/` 下的配置模板，写清真 Docker 测试的前提、跑法及哪些会调用真模型。先验「自己照 README 能跑通一次任务」，阶段 2 再验「别人能跑」。

## 制造闭环

一个主体在运行中造出另一个主体，交办一件事并审阅结果；有文件产物时再按工作区规则并入。它检验「Definition 与 Charter 是数据」的设计，以及授权只收窄、修正权独立、可追溯在应用组合中的落实。分三步，前一步不通不做后一步：

1. **Cognition 版**：W0 经工具构造一份 Cognition Definition，实例化、交办并收取结果。代码依赖取自自己 Definition 的完整 Bundle，模型碰不到 ID。不依赖 Kernel 的新功能；当前证据与限制见「现在」。
2. **模板与说明**：Library 的包里提供 Charter 生成函数（N 个同样的 Seat、审计者、熔断者）与可运行的例子，经管理器给出，模型选模板、填参数，不手写整份 JSON。
3. **Charter 版**：同样的流程，造的是 Charter。依赖 Kernel 的构造检查（pin 的 Definition 满足 Seat）、终止闭环与对 Collective 的 Correct，见 croon:docs/Kernel/Definition/README.md「检查」与 croon:docs/Kernel/Instance.md「待定」。Cognition 的实验不等待这些工作。

验收分为机制与使用两组。

**机制验收**：

- 不同形状的主体可构造和运行；源码错误带位置与原因返回，输入与接线错误能被拒绝；结果及依赖经 Notify 正确返回。
- 新制造路径覆盖 infer、pack、construct、instantiate 与结果收取的关键提交窗口，中断后重跑结果相同；再补执行在途时的进程中断，已有路径的恢复测试不替代这些验证。
- 委托深度按 Library/Runtime.md「不建议委托超过两层」的默认接线写进场景。
- Charter 阶段另验构造、终止与 Correct，并用检查器查出「审计者被执行者控制」等图性质。

**使用验收**：在固定模型、说明、任务和修复预算下，记录构造、运行与任务验收各阶段的结果。真实模型须能根据任务写出主体、理解反馈并修复，最终通过独立判据；成功率、修复成本与耗时由实验给出。修复预算用尽时保留完整尝试，分析失败原因；是否改用模板或 Library 生成，由对照实验决定。

制造闭环之后，「跑通」以下面两条为准；Application（收什么见 Library/Presets.md「Application」），如个人生活管理，排在它们之后。

- **一天内复刻**：市面上任何一个 Agent 框架出现，不到一天就能用 Croon 把它的核心逻辑写出来，并且同样用 Croon 写出它的测试、跑完。复刻的是核心逻辑，不是源码。复刻不出的，就是 croon:docs/Kernel/README.md「运作方式」的缺口。
- **复刻者**：造一个专门制造或复刻别的 Agent 的主体，它把做过的经验存下来，拿到一个 Agent 的源码或文档架构，就能批量复刻。

复刻的对照：别的框架回答过的问题，Croon 都要有一个落点。先做 DSH（DeepSeek Harness）：它用到的技术各回答什么问题，Croon 用什么组合回答；结果进 Research，缺口进 croon:docs/Kernel/README.md「运作方式」。

## 测试

| 验证方式 | 能证明什么 |
|---|---|
| 脚本化模型与真实执行 | 指定路径的机制、交付、接线和结果处理成立 |
| 录制与回放 | 固定请求与结果下可重复运行 |
| 故障注入、进程中断 | 被覆盖路径的恢复行为成立 |
| 真实模型与固定检查器 | 在给定任务和条件下的实际完成能力 |

- **场景**：Library 的场景预期在 Library/Scenarios/，测试拿真的 Kernel 与 Lang0、假的模型与文件执行驱动，逐提交点与逐 provider Atom 在途崩溃比对 Journal；预期由 CPython 独立求出并核对。
- **端到端**：host 中需要真 Docker 的集成测试标了 ignore，依赖本机的 croon-work:1 与 python:3.12-slim；ignore 表示默认跳过，不表示未经运行。模型通常用脚本化或回放的，录像只在临时目录。`smoke` 调用真模型，会产生费用，目前主要断言运行完成、结果目录存在及录像不含凭据，不替代任务正确性检查。
- **恢复覆盖**：`recovery` 覆盖预置交办路径的逐提交点中断；`kill` 覆盖 exec 在途 SIGKILL；`failure` 覆盖宿主故障后修好重跑。跨 Kernel 目录比结果与记录序列，同一目录内逐字比。`construct` 验证构造后以空录像重跑，`agent` 验证文件型制造路径的完成与跨系统回放；二者尚不能证明该制造路径在各提交窗口中断后都能恢复。
- **实验记录**：保存任务、判据、模型与说明、代码版本、修复预算、源码尝试及每轮失败的 kind 与 message。记录失败阶段、修复次数、检查结果、模型耗时与用量、exec 次数与耗时；较长任务和持续运行实验追加内容库大小、恢复时间、tombstone 数量。任务未完成、宿主故障、检查器故障分开统计。
- **独立验收**：检查器由实验方固定，被测主体不能修改；检查实际结果的正确性，不只看退出码，必要时加超时与资源限额。失败尝试也保留记录。

## 以后的方向

按需求或实测结果启动，不作为近期实验的统一前置条件：

- **持续对话**：任务需要运行中追加输入、反问或干预时，推进经 socket 的 root entry、软打断与硬打断；场景见 croon:docs/Kernel/README.md「W0 持续对话」。
- **运行成本**：测到对应成本妨碍目标任务时再优化。Checkpoint 降低重放计算成本，存储去重降低内容库增长，执行提供者与调度优化降低调用开销和等待成本，分别验收；tombstone 的处理须维持 Directory 的退役保证。
- **Charter**：开始组织型实验前补齐「制造闭环」Charter 版所依赖的正确性缺口。
- **实验台做成 Definition**：任务协议、评价与记录方法稳定后，把已有实验能力组合成专门的 Definition，跟它说话就能提实验、看结果；复用通用交办与固定检查器，被测主体不自评。
- **场景同步工具**：随实际改动减少 Interface、工具说明等派生数据的手工维护；关键行为预期保留独立来源与明确断言，不由被测实现自动生成。不作为实验的前置大项目。
- **写回仓库**：在结果目录已不足以满足使用需求时推进，以导入时的目录 Bundle 为基准并回用户仓库，冲突时报告；见 Library/Organization.md 的待定。
- 联网：可用性要它。做法在 croon:docs/Kernel/Reference.md「通道」与待定；第一版不联网。
- 历史管理：执行恢复依赖 Journal 的分叉待定。
- **语言摩擦对照**：当近期实验反复撞到 Lang0 的表达限制时，为同一场景分别写普通 Python 与 Lang0，逐处说明差异及其原因，检查是否存在未报告的语义变化。模型完成能力的量化按「下一步」与「测试」推进。
- Provider 的管理面：KV Cache 的管理、推理的控制面。前缀复用现在只能在基础设施一侧做，经 HTTP 够不到；线索见 croon:docs/Kernel/Port.md 的待定。排在靠后。
- 生态入口：经 MCP、A2A 接别的框架与客户端，Croon 作调用方或被调用方。依赖联网与系统边界，排在阶段 2、3；见 croon:docs/Kernel/README.md「待定」里的「系统边界」与 croon:docs/Kernel/Plugin.md「待定」。
- 独立软件交付：是否把一份 Application 连同它的 Definition、资源、界面与 Kernel 运行时一起打包，安装后即可使用；运行权利与凭据由部署时的根接入。内嵌运行时、容器依赖、安装与升级，等首个 Application 的场景明确再定。
