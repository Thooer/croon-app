# 实验

回答一个问题：真实模型在给定任务与条件下，能不能写出、造出、用起一个主体，卡在哪个阶段。机制、判据与记录写在这里；任务与检查器是 `experiments/` 里的数据与脚本；结果不进 Git。设计依据见 Plan.md「下一步」第 3、4 步与「测试」。

## 一次尝试

一次尝试是：一个任务，一个模型，一次 `croon-app run`。过程由实验脚本驱动，流水固定：

1. **准备**：为这次尝试建一个临时目录，里面是任务的初始仓库、复制来的模型配置、一份 host.config。每次尝试用新的 Kernel 目录。
2. **运行**：`croon-app run`，模型配置选录制，所以模型往来都落进这次的录像。载入的工具清单由任务给：测制造的任务不载入预置的子代理。
3. **遇到宿主故障自动续做**：模型服务断连、超时这类宿主故障让 Kernel 停下 Instance，`croon-app` 带着原因退出。脚本对同一个 Kernel 目录 `croon-app resume`，最多 3 次，每次计入记录的「宿主故障」。三次还不行，这次尝试记为宿主故障。
4. **验收**：运行结束之后，由检查器判定，不看 W0 的转述。
5. **记录**：写一份记录文件。

## 任务

一个任务是 `experiments/tasks/<名字>/` 下的目录：

| 文件 | 内容 |
|---|---|
| `task.json` | 任务的文字，类别，载入的工具清单，要不要初始仓库 |
| `repo/` | 初始仓库，可没有 |
| `check.py` | 检查器：收到这次尝试的目录，打印一个 JSON 判定 |

类别只有三种，对应「制造闭环」里主体的三种形状：

- **compute**：纯计算，没有目录也不用模型。检查器从录像里取出造出来的源码，用 `croon-app exec` 在检查器自己的输入上再跑一遍，比较结束值。答案写死、只对任务给的那个输入对的主体，在这里被识破。
- **files**：改文件。检查器拿结果目录，在宿主上跑隐藏的测试。隐藏测试不进初始仓库，主体看不到。
- **model**：用模型。检查器从录像里取出造出来的源码，核对它确实调了模型（源码里 import 了 `library.model`，录像里有对应的子调用），再核对输出满足任务给的可检查的约束，如长度、格式。内容好坏不评。

检查器的判定是 `experiments.verdict`：

```
{"passed": bool, "reason": "一句话", "details": {...}}
```

检查器自己出错是「检查器故障」，不记为任务失败。

## 记录

一次尝试一份 `record.json`，在 `experiments/runs/<批>/<任务>/<序号>/`：

| 字段 | 内容 |
|---|---|
| `task`、`model`、`commit` | 任务名、模型名、两个仓库的代码版本 |
| `outcome` | `passed`、`failed`、`host_fault`、`checker_fault`，四种分开统计 |
| `stage` | 失败的阶段：`look`、`make`、`construct`、`run`、`merge`、`answer`，没失败为空 |
| `model_calls` | 模型调用的总次数，与各自的输入输出 token |
| `makes` | 每次 `make` 的尝试：源码、成败、失败的 kind 与 message |
| `host_faults` | 宿主故障次数与原因 |
| `seconds` | 总耗时 |
| `verdict` | 检查器的判定 |

记录取自录像与脚本的计时，不为实验在 Library 里加埋点。`stage` 与 `makes` 从录像里的工具调用与工具结果推出：`make` 调用的结果是错误就记一次失败尝试，错误的 kind 与 message 原样记下。

## 批与统计

一批是同一个模型、同一版代码下，一组任务各跑若干次。批的汇总按任务给出：成功几次、失败在哪个阶段、`make` 平均几次才过。**少量任务的成绩不作总体成功率**：汇总只列事实，不求平均成功率，也不给排名。

模型调用的费用靠 token 数估计，不记货币。

## 范围外

- 不评内容质量：口号好不好，不是这里的问题。
- 不比模型：同一批只用一个模型。
- 不做持续对话与多主体协作的任务，等 Plan「以后的方向」里的那些条目。
