来自 docs-v1（Harness 的可视化规格与 29 轮问答）、docs-v2、docs-v3。旧稿的对象（Session、Task、Run、Step、Action、Point、Allocation）在当前设计里不存在，要重映射到 Instance、Journal、Atom、Tree、来处树、派生树、Charter 的接线图；下面只留与对象无关的原则、你的裁决的意图、与当前设计的接缝、待核验的技术线索。

#### 原则

- **直接呈现拓扑**（v2）：领域模型本身是拓扑，可视化直接呈现它，不在领域模型之外另造表示层；每个交互是一次保持不变量的拓扑操作。核心结构靠图形本身（节点位置、连线方向）可见，颜色、标签、工具提示只是辅助：不允许用户要点开节点才知道类型、要看颜色才区分对象、要读标签才知道两个节点的关系。待验证的五条约束（原文自称望文生义）：Object Constancy（对象保持稳定的视觉身份）、Spatial Continuity（位置连续变化）、Semantic Zoom 与 ZUI（不同缩放级别不同详细程度）、Shared Element Transition（同一元素在视图间平滑过渡）、Motion Continuity，合起来是「无跳变」。实现建议：历史前驱与来源边分别展示，不把来源边画成第二个前驱；任务关系用卡片，分解边向下、前驱边向右；文件谱系用 Git 的图。
- **投影不是第二事实源**（v1）：只消费已提交的事实，不新增持久关系或投影状态表；画布不改领域身份、关系种类、provenance 与 source_path；画布与传输层的动作不伪造领域状态（取消传输不等于取消运行）；局部（路径级）的事实可以在总览里给摘要，但不聚合成整体的状态。
- **不补边**（v1）：不按时间、序号、数组位置、布局、名称或类型邻近补造关系；没有唯一来源或对齐证据时，保留已有的片段并显式标记截断，不生成端点不存在的边；折叠或聚合后的连线必须能追溯到完整的来源路径。
- **不同种类的边不合并成一张图**（v2 的 Lineage，v1 的 Unified Graph Relations）：每个视图写明参与遍历的边与方向；v1 把边分成 persisted_fact（权威事实）、derived_relation（带完整查询上下文与 source_path 的快捷关系）、visual_projection（布局、轨道、聚合、虚影、命中区，不参与领域遍历）；「创建来源」与「结果引用」可能指向同一个节点，不靠拆节点或删来源规避，而是明确它们不是历史前驱、不一起充当因果顺序；用线型、标签、方向区分，每一种都不伪装成另一种，非当前的关系退弱而不删除。对照 Journal.md「来处树与派生树是两种投影」。
- **三种 key**（v1）：domain_key（对象的稳定身份）、representation_key（视觉实例，同一对象可有多个）、transition_key（连续转换）；预览、未提交的输入目标、分叉锚点用独立的 representation_key，与实体共享 domain_key 与 transition_key，这就是「虚影」。
- **snapshot 加 patches 等于 snapshot**（v1）：二者经同一个 canonical reducer 得到相同的 semanticHash（只覆盖身份、关系、状态，不含布局、时间、数组位置、相机）；DTO 带 query identity、投影版本与 generation（与数据无关，用来拒绝旧代的 cursor）；重复可幂等接受，乱序、缺口、旧 generation 不得静默接受；cursor 在整批归约提交之后才推进；patch 归约拒绝改写身份、改写关系、悬空的 tombstone。
- **焦点相互独立**（v1）：计划焦点、运行焦点、阅读焦点、选择、输入目标、相机，不能互相推导；焦点失效时回到根，不按时间、序号或布局猜测替代目标。
- **输入目标是强边界**（v1）：提交时由后端固定成合法的位置，任务或运行只是提示；目标无效报校验错误，不静默改选最近的位置，也不在提交或认领之后改绑；取消目标不丢草稿，提交中禁止重复提交；输入的状态：draft、validating、submitting、accepted，然后是 claimed、retryable_failed 或 target_invalid。
- **聚合与渲染的边界**（v1）：聚合、边捆绑、layout、virtualizer 不得跨关系种类、改身份或补造拓扑；虚拟化不丢焦点、可访问名称、详情的目标、输入草稿与锚点，重入视口时从原锚点恢复；状态更新只触发受影响的局部，不重排全图；颜色只表状态，状态与关系不只靠颜色；把「未了结」（对账中、清理未完成）与「已到安全终态」分开显示。
- **连续性**（v1）：无跳变；展开从所属锚点附近生长，收束回同一锚点，粗表示是细表示的 representation ancestor；展开增加所在路径的局部空间，后续节点沿路径让位，不靠向右追加一整列；新意图打断动画时从当前插值状态重定向，旧回调不得覆盖新焦点；减少动态效果时必须到达相同的语义终态（你在第 23 轮说暂不处理）。
- **折叠深度**（v1）：是同一张图的全图统一语义层级，不是按实体类型分栏；固定档位时缩放只改相机尺度，自适应档位按节点在屏幕上的可读尺寸决定展开深度，阈值带滞回，避免在边界反复展开收束；点击展开与按钮切档用同一套变换；自适应切档不自动 fit 全图、不抵消用户正在进行的缩放，焦点或缩放位置保持为相机锚点。
- **交互语义**（v1）：悬停是临时感知，点击是确认选择，滚轮改变空间尺度（可组合修饰键；非对话形态下只能拖动或 shift/ctrl 加滚轮上下滑动，展开成对话时才能直接用滚轮）；悬停与键盘焦点等价；悬停预览用「交互走廊」保持可操作，预览树里再悬停节点是二级预览，内容按状态自适应；滚动、详情、目录树与主画布各自消费滚动，惯性不跨空间触发导航。
- **信息承载**（v1）：对话气泡内放理解当前消息的局部状态；就地卡片放「这是什么、为何在这里、当前发生什么」，至多一屏；右侧面板放完整字段、事件序列、来源图、文件差异等审计内容；同一事实只有一个完整的展示位，其他位置给摘要与跳转（与 AGENTS 的唯一出处同一个思路）。
- **对话是图的一种展开状态**（v1，你确认的模型）：没有独立的对话面板，消息节点拉伸成气泡；紧凑态不是细节变少，只是拉伸得短；不可继续的节点（没有检查点、调用未配对、失败的中间态）禁用输入。

#### 与当前设计的接缝（推断，没验证）

- **Feed 就是读取加同一个归约**：v1 的 snapshot 加 patches、cursor 在整批归约后才推进、旧 generation 被拒，与 Plan.md 的 `apply(索引, 记录) → 索引`（写记录与重建索引共用）是同一个归约；前端的 Feed 可能就是「看」的读取（带 from 序号，Port.md）加这个归约，不需要新机制；v1 的 generation 在这里的对应物要想一想，它是投影版本，不是代际号。
- **跨 Journal 的实时订阅**：v1 的 feed_position 是事务内的传输位置，与 Event 在 scope 内的 sequence 分开；v4 每本 Journal 有自己的序号，驾驶舱要同时看几本，需要一个跨 Journal 的 cursor，现在没有（Draft/README.md 把「全局事件表现在就做」列为否定，等查询需求出现）。
- **折叠的坐标**（v3）：认知模式在运行时保留为一层帧，不在构造时内联展开，可视化的折叠单元与委托者观察的粒度靠它；函数没有自己的求值（Journal.md），帧由重放算出，不进记录。
- **静态骨架加运行时展开**（v1 的 research/workflow/update.md，别的 AI 的建议）：静态的阶段与路由供可视化，阶段内动态；编译器只认 parallel、pipeline、循环这类可识别的模式（在 AST 里数 fan-out，数不出的记为 dynamic），其余黑盒；不要试图编译任意代码，不要强制用户用 DSL；渐进：纯动态、加静态阶段声明、识别并行与流水线、细粒度依赖追踪。对照 Lang0：构造时本来就在 Python 的 AST 上做分析（规则 3、闭包捕获），骨架（循环、with ProcessPoolExecutor、对 Port 的调用）可以从 AST 取，运行时的展开由键与 Journal 给，不需要另一份 IR。呼应你上面写的「认知需要下苦功夫，好像可以用控制流提取结构的库」。
- **多客户端**（v1 的 Q&A）：四版演进：GUI 自己有更新机制（GUI 听 CLI，CLI 每次命令都是最新状态）；事件扇出做动态更新；同一时刻只有一个前端能对进程写；同一时刻只有一个前端能对同一个对话写。对照：根的入口是求值器在系统外的 Instance，一个客户端连上就取得执行权、代际号加一、旧会话被拒（Cognition.md）；读是另一份「看」，可以有多份；所以前两版是读侧，后两版是写侧，写侧的粒度就是 Instance。
- **三种视图与分支同构**（v1 的 Q&A，你的原始描述）：一个 Session 是一棵消息树，不合并时与工作树的分支一一对应，每个分支可单独运行；消息树到上下文是树到链，量级不同，需要压缩节点平衡；文件树也要可视化并与前两者有关系；层次之间不能跳变。前半是 Organization.md「历史分支与合并」的同构要求；可视化要同时给三样：消息（历史）树、文件树、由树生成的上下文链，它们之间的切换不跳变。

#### 你在 v1 里做过的裁决（意图级）

问答里的 Invocation 在 v1 后来改称 Run（一次 Agent 循环）。

- **总览**：回答「我有哪些工作」，默认少量摘要，可悬停预览或动态展开，不能同时显示所有东西；默认不出现检查点与位置、Git 提交、步骤、消息节点。
- **两种投影，同一批对象**：Session 中心（Session 是纵向的一条链，旁侧是工作空间树，Session 之间不连边，默认按用户最新消息的时间降序，可切换排序）与 Workspace 中心（Session 像子节点挂在文件夹上，一个 Session 可有多个文件夹父节点）；两种投影下工作空间树都在画布最左侧；切换用非线性转场，Session 顺着连线移动、相机左右移动；首次打开 Session 中心，之后记住上次的投影。
- **工作空间树**：由 Session 真实访问过的文件夹构成的森林；共同根只是可视化容器，路径拓扑上存在共同祖先才合并，证明不了关系的保持为同层的根；按真实分支展开。
- **悬停与进入**：悬停 Session 出现横向的「虚影树」，预示它内部的运行轮廓（几乎没有文字，只带最新一端的简化消息与位置，运行中的有轻量标记）；鼠标可以移进虚影树，再悬停某个节点看二级预览；点击虚影树上的位置是导航到另一张图上的位置，目的是省去来回翻找；点击后虚影旋转实体化，进入 Session 主图。
- **Session 主图**：自上向下生长，分叉是真实的树结构（像 VS Code 的 git 图），不设「主分支」（第一版引入是负担）；Session 节点是视觉根，不是消息树的领域父节点；四级折叠；动画语法是生长与收束。
- **运行的折叠形式**：「锚点加轨道」，锚点保留身份与状态（运行中、暂停、完成、等待输入、中止），轨道只作弱标识；压缩节点的子链侧向展开（仍然自上而下），默认画来源边。
- **文件轴三级强度**：常态只在锚点或末端做边界徽标；叠加时出现一条与主干平行、跟随聚焦分支的稀疏检查点轴；审计时文件轴升为主结构，展开提交图。提交节点严格只在检查点引用了新的 Git 提交时出现；用户或外部进程改了工作树，先出检查点，后出提交；触发：文件轴按钮、选中时显示、变化时提示、目录树联动；继续输入的目标边界由「位置」决定。
- **目录树**：只在 Session 内、按钮开关；范围取事实（真实访问、修改或作为边界记录过的目录），保持真实的树、无分叉的中间目录折叠成一段；悬停图上的对象，高亮目录树里对应的路径，悬停目录节点，高亮主图里对应的位置，没有对应事实时不制造连接。
- **图上对话**：点击一个运行，图的最下层长出输入框，图上用带明暗变化的虚影标出「现在发送会注入到这里」；点击正在运行的那条链，整条链向右拉伸成消息气泡，默认拉伸当前这一条，向上的祖先以较紧凑的气泡延伸；三种输入：接到最末端（正常往下长）、在中间分叉、不可继续的节点禁用输入。
- **详情三种承载并存**：气泡内的局部、就地展开的卡片、右侧的传统面板，有重叠但互补。
- **视觉**：同源形态；颜色只表状态；运行中局部低频运动；转场强、日常弱；明暗双主题；高密度克制；节点标签语义名称优先；输入框按选择生长；窄全局栏加全画布；控件放在画布边缘。

#### 技术线索（待核验）

- **现成图库不够**（v1 的 Q&A，别的 AI 的回答）：React Flow、G6、Cytoscape 解决的是单一图的编辑与布局；要的是语义缩放、拓扑变换动画、多视图协调（消息树、文件树、上下文链的关联与同步高亮）、形态学连续过渡，即一个可编程的布局加过渡系统；领域的投影引擎（关系种类、消息树到上下文链、压缩节点、表示的层级、Git 轨道、文件投影）必须自研，没有通用库能替你决定。
- **ELK 不能当空间语义的 source of truth**：官方的 interactive layout 只是「尽量少改已有布局」，官方自述有些约束「requires more than ELK can deliver」；已知问题：collapse 后兄弟顺序与固定的根被挪动（eclipse-elk/elk#1016，抓取时仍 open）、interactive constraint 的长期异常（#883）、layered 加 INCLUDE_CHILDREN 加 FIXED_ORDER 端口加跨层级边会触发内部异常（#1192，elkjs 同样复现）。建议：领域图 → 领域自己的 rank、lane、锚点 → ELK 只解局部的 packing 与 routing → 世界坐标，这样 ELK 重排失败不会破坏语义轴。
- **不跳变靠 projection contract，不靠 layout 引擎**：GraphMaps（Microsoft Research）预生成一系列 refinement layers，缩放时选层并限制视图内的实体数，要求各层几何稳定。对应：一张稳定的领域图 D，各语义尺度的表示 R0(D)→R1(D)→…，要求 parent(R_{k+1}(x)) = R_k(x)，于是每个新表示有出生锚点，每个被聚合的有死亡锚点；P_fine(child) = P_coarse(parent) + Δ(child)，过渡带里 P(t) = (1−t)·P_anchor + t·P_fine，透明度、尺寸、标签细节与边的拓扑分阶段插值；边也一样：聚合边 → 捆绑的关系 → 具体的边，粗边必须是细边束的 representation ancestor，不能直接对两套无关的线路做 crossfade。
- **yFiles 值得 spike**：增量布局明确区分固定的（sketch）与增量的元素，目标就是保持 mental map；LayoutExecutor 的 anchored item（官方例子：展开或折叠分组时固定一个节点的角，使按钮仍在鼠标下）；PartialLayout 只布局指定子图；原生的 Level-of-Detail；SVG 与 WebGL 混合；商业许可。要测的三件事：representation refinement 的转场、ELK 在硬的领域锚点下能承担多少局部 routing、yFiles 的增量与锚定能省掉多少自研。
- **React Flow 的性能与动态图实验**：复杂 SVG 边下 50 个节点就可能出问题（xyflow/xyflow#4617，另 #3003 问 1000 以上），所以要 benchmark，不是现在迁移；Canvas 与 WebGL 只留逃生口。动态图实验：一项综述指出没有一致的证据说明「已有节点尽量不动」总能改善理解；另一项里 small multiples 总体更快，动画在「识别变化」类任务上更准（ScienceDirect S107158191300102X）。因此连续动画的更强理由是解释表示的转换本身（这个任务展开成哪些步骤、这些消息怎样收束成压缩节点），即用运动表达 provenance，而不是为了保持 mental map。
- **路线**（v1 的 ROADMAP/VISUALIZATION）：fixture、DTO 与 checker（B0）→ snapshot、patch、feed（B1）→ 交互连续性（B2）→ renderer、layout、virtualization 的正确性（B3，正确性、可访问性、焦点、关系种类、source_path 是硬门）→ 性能与选型（B4，同一 fixture 与设备，正确性失败不能由 FPS 抵销，最终选型由用户确认）→ 真实切片（B5，只消费真实的投影 DTO）。U2 待确认：最低设备、辅助技术、时间线语义、延迟与帧时间与内存预算、是否允许 Canvas 或 WebGL 配合 DOM 与 ARIA。
- **前端工具链**（v1 的 ROADMAP/STATUS，已验证）：TypeScript、Node.js、Electron、React、Vite 可构建；开发模式与 AppImage 可渲染 React；file:// 静态资源加载、测试、生产构建、AppImage 打包通过；坑：同名 AppImage 运行时不可覆盖，否则报 ETXTBSY；尚未配置应用图标。Kernel 现在是 Rust，经 Unix socket 的会话（Implementation.md），前端用什么还没定。

8，前端的推导：

**1. 自动生成只读 Interface，不读 body、不读 AST。**
Draft 的线索说“认知需要下苦功夫，好像可以用一些控制流提取结构的库”。我的结论相反：UI 生成只从 Interface 出，body 内部的控制流不自动画。理由是 Interface 是唯一稳定、别人依赖的外部模型，body 是 Implementation，别人看不到，画出来也只是猜测。这条和 Draft 线索有张力，我认为应该放弃那条线索里的“控制流提取”。

**2. 绑定分两段：静态段从 Interface 生成骨架，动态段把 Handle 绑到元素。**
文档说“操作的是结构与权利”“交互协议读取附加结构”，但没说 UI 元素和 Port 怎么对上。两段式（结构从 Interface 生成，句柄在运行中绑）是我推的。

**3. Schema 到控件的映射是一个纯函数。**
文档说 value.schema 既校验又给 LLM 当工具说明。我推：它同样能驱动 UI——object→卡片、array→列表、enum→下拉、anyOf→条件渲染。同一份 Schema 的第三种用途。

**4. 旁路 UI 描述必须不进语义、不进 ID，且没有它时要有默认布局。**
Draft 说“附加结构信息，读取方是交互协议”，带问号，没定它怎么和 Definition 的身份相处。我推：它不能进内容寻址（否则同一份 agent 因 UI 不同就成了不同身份），构造时忽略，前端读取；缺失时按 Interface 生成默认布局，否则没有描述的 agent 不可用。这同时回答了 Draft 那个问号：读取方是前端，Kernel 完全不碰。

**5. 好看不靠生成，靠组件库加旁路描述。**
文档不谈“好看”。我的结论：生成只负责选控件和布局正确性，控件长什么样由手工组件库定，布局顺序与强调由旁路描述定。生成保证不出错，手工保证好看，两者不混。

**6. 前端自己是一个 Cognition，有 Journal，它的操作可追溯可撤销。**
Draft 说前端是普通参与者。我推得更硬：它不是一个特殊的 UI 层，而是一个按 Definition 行动的 Instance，持有 Port，每次点击是一次 Atom，记在自己的 Journal 里，所以谁在什么时候点了什么、能不能撤销，都有记录。这让“驾驶舱”和“被驾驶的 agent”在同一套规则里。

**7. 前端的权限就是它持有的 Reference，UI 上不显示它没有的 Reference 对应的操作。**
这条从 Reference 的一般规则直接推，但推出来有一个具体结论：UI 的可操作集合可以由 c-list 在运行前算出，所以“这个用户在这个 agent 上能点什么”是静态可查的，不是靠前端隐藏按钮。

**8. 写侧粒度是 Instance，前端要改一个 agent 的运行方式只能 Handoff，不能在 UI 里原地改。**
从 Instance 不换 Definition 直接推，但落到前端上有一个具体含义：UI 里“改这个 agent 的配置”不是一个表单保存，而是一次构造加 Handoff。这决定驾驶舱的交互形状。

**9. 投影是纯函数，所以视图可以离线重建、可以测试。**
文档说投影不是事实源。我推：既然是记录到视图的纯函数，视图就能从 Journal 离线重算、能对固定输入做断言。这给前端测试一个落点，不需要跑真的 agent。

**10. 前端不持有目标 agent 的 Correct 时，界面上就没有暂停按钮；持有收窄过的 Correct，就只能显示对应的操作。**
这是“授权只收窄”在前端的具体形态：UI 按持有的 Reference 的链上每一节生成可操作项，不是按角色或配置生成。
