# 包与管理器

Library 是一个目录，里面是一组包与工具清单。管理器是 W0 的几个工具：看、造并载入、并入；设计里还有装与留存，现在没有。载入的东西就是工具。本文写包是什么、目录属于谁、怎样留存、管理器管什么。

## 包

包是一个子目录，里面是 Lang0 模块，带一份手写的 README.md，说明它是什么、怎样用。所有包并排放在 Library 目录下，那个目录就是 import 的起点：`import library.files` 找名为 library 的包里的 files.py。装载的语义见 croon-lang0:docs/README.md「模块」。

- **主体也是包。** 带入口模块 `main.py`、其中有 `main` 的包就是一个可以实例化的主体。App 自带的主体（W0、s）、用户写的、运行中造出来的，都是同一种东西：一个目录，一个入口。包名由造它的一方起；运行中造的，名字是模型自己起的，满足 README.md「模型看到的名字极简」。
- **公开面**：名字以下划线开头的不公开，不进索引。
- **索引**：宿主从源码推出，规则与推 Interface、`croon.tool` 的说明相同：签名、类型、docstring 与其中的 `Args:`，Port、TypedDict 与 Schema 一并收。索引是源码的派生物，从不落盘：导入时由宿主为每个包推出，运行中新装的包经宿主的推导 Port 现推，见 ../Host/README.md「构造的推导」。所以它与代码永远对得上，没有人能把它改旧。
- **按层展开**：一句话（包的 docstring 首行）、README、模块索引、某一项的签名与说明、源码。模型按需要往下读，每一层作为工具结果进入历史；常驻的只有每个包一行。
- **例子**是包里可以直接运行的主体。测试负责构造并运行它们，例子因此不会过期；模型可以照抄它的源码，也可以直接载入它。
- **生成模块**由宿主生成，导入时放进目录 Bundle，重放不随宿主构建改变类型，不进 Git，也不写回：library.kernel 只提供 KernelPort 的 Port spec 与 Outcome；library.model 的 Generate 来自 model.generate；library.directory 的 Exec 来自 directory.exec；library.infer 的 Infer 来自 definition.infer；library.tools 列出诞生时可载入的函数工具包，见 Runtime.md「工具」。生成器在本仓库。

## 管理器

管理器是 Library 里的函数，不是 Definition，也没有自己的身份，作为 W0 的工具。现在有的是 `look`、`make`、`merge`，各做什么见下面的表；「装」是设计，见「目录与留存」。

## 目录与留存

**现在**：Library 目录是仓库根的 `library/`（手写的包，编进二进制）加生成模块与默认的工具清单 `tools.json`（形状是 `home.tools`，源码在仓库根的 `home/`）。每次运行开始时，宿主把它们装进一个临时目录、导入成目录 Bundle，交给 W0；运行结束，这份 Bundle 就随这次运行结束，**不写回磁盘，下一次运行重新开始**。配置里没有它的路径。没有分层：App 自带的包、运行中造的主体并排放在一起。

管理器现在有两个操作：

| 操作 | 现在 |
|---|---|
| 看（`look`） | 做了：不给名字是 README 与各模块的一句话，给模块名是它的公开面，`source=True` 是源码。只读目录，不起 exec |
| 造并载入（`make`） | 做了：模型写源码，造出 Agent，载入工具表，下一轮起直接调用。它只活在这次运行里 |
| 装、留存 | **没有**：不能把一个包放进磁盘上的 Library 目录，造出来的主体下次不在 |

**设计，还没有实现**：

- **Library 目录在磁盘上，路径写在宿主配置里**，顶层是各个包与工具清单。
- **留存就是采用。** 运行中装的包、造的主体、改过的清单，是对这个目录的改动，作为候选交回，由用户显式采用，写回磁盘，规则与任务目录的采用相同，见 ../Host/README.md「结果与采用」。用户用 git 看 diff、决定要不要。不采用，这些改动随这次运行结束；采用了，下次运行导入时就在。
- **为什么在磁盘上，不在系统里由保管者持有**：它属于用户，用户在系统外；导入与写回是根在系统外的事，与任务目录同一个位置。用户能用编辑器看、改，用 git 管。保管者能给的历史与共享，这里由 git 与三方合并给出。
- **在系统里是一个工作区**：宿主导入后交给手，手的「装」「载」移动它的当前位置，规则见 Runtime.md「工作区」。它与任务目录是两个工作区，当前位置各自移动；交回时各是一份候选。
- **「装」**：把一个包放进 Library 目录，来源是模型写的源码、任务目录里的一个目录，或以后的联网下载。派生新的目录 Bundle 再采用；能 diff，能回滚。造一个主体就是装加载。模块也能装：装上的只有被载入或被 import 时才生效，影响只到用户自己以后的运行，且要经采用才落盘。
- **不分 App 与用户两层。** 本机从仓库运行，生成模块每次重新生成，不会与宿主错位。以后把 App 打成安装包交给别人时，App 的包随版本更新、用户的包留在用户那里，要分层，那是打包的事，见 Plan.md「以后的方向」。
- **人与手是同一组操作**：人经客户端做的看、装、载与手经工具做的落在同一份实现上；人也可以直接改磁盘上的目录，下一次运行导入时生效。

## 待定

- 联网下载包：依赖 croon:docs/Kernel/README.md「待定」里的「系统边界」。内容寻址的哈希就是锁定。第三方的包没有环境权利，只能用接给它的 Reference，所以风险只有两处：接给它什么，以及它的输出对模型的影响；后者在作者与使用者不再是同一个人时才出现。「装」的来源留成可以扩展的形状，接上联网时不改它的用法。没有场景。
- 多库组合：不同的包同时载入时，要不要识别组合、给结合使用的教程；识别到什么程度。没有场景。
- 每一层展开给多少内容：由实验定，见 ../Experiments.md。现在只试过一种（概览一句话、模块的公开面、源码），够用，没有对比过别的。
