# 组织与历史

共享与保密、连续的地址、Handoff 与历史分支与合并：Principal 怎样组织多个 Cognizer，并保持连续与历史。

## 共享与保密

Kernel 默认谁都读不到别人的东西：每个 Instance 只取得显式交付的内容；其他材料要经 Port 的 dependencies 拿到。所以共享与保密都是扩展，由一个持有状态的成员决定；暴露什么由它负责，见 ../Kernel/README.md 的「放置」。下面是具体做法。

- **状态的保管者**：读的 Port 交给几方，就是共享；只交给一方，就是保密；开一个带合并规则的写 Port，就是共同编辑。读到什么粒度，就是它开哪几个 Provided port：全文、摘要、只看结构，各是一个 Port，可以交给不同的一方。共同编辑时，别人交来一份目录 Bundle，它按规则合并：路径不同直接合并，冲突时按内容的规则处理；它记下这次并入，回复新 Bundle 的 ID，读者向它要当前 Bundle 的 ID；结果可以写明基于哪个版本，回滚就是指回旧的 Bundle。数据库的视图与授权、文档的查看与编辑角色、RBAC、ReBAC，都可以作为它的判定写法。分享链接对应的是一个可以转交的 Port，不是一个知道就能用的口令。
- 提供这个工具的也可以是外部服务，如一个数据库：状态在外部世界，Croon 只记下通道上的往来，不能重放，中断时记为 unknown。Croon 不镜像它的状态：镜像是第二份事实，与外部对不上时没有权威。
- 要让保管的规则归组织，用 Charter 的刚性；状态的主人仍是保管者，责任看来处。
- 工具不发知道就能用的字符串票据：这样的票据在别的工具上没用，在同一个工具上谁拿到谁能用。可转交的东西用附带给出，Kernel 记下派生、能撤销；工具内部的名字只按来路解释。Kernel 管不到工具内部，这是工具作者要守的规则。
- 全局的共享就是 root entry 实例化、一路接下去的一个保管者。全局只是说谁都够得到它，由 root entry 的接线决定；每次访问都有记录、能撤销。所有人默认都够得到的共享空间是环境权利，不设。
- 谁可能读到某样东西，从接线与附带的声明算得出：看谁能经 Port 够到持有它的成员。所以「私有数据分给不同的成员」可以由检查器查。
- 秘密不写进 Definition：能实例化一份 Definition 的一方，读得到里面写死的东西；代码也一样，import 它的一方就在自己这边求值。秘密也不写进交给 llm 的 Value：那是接上的引擎的提供者看得到的。
- 只看结构的 Port 要把 ID 遮掉。内容熵低时，ID 本身就是信息：拿到 ID 的一方能对猜测算哈希、比对，确认内容。

## 连续的地址

Kernel 不换人，见 Definition 的 Seat 与 Instance 的同一性；要给别人连续的地址，就由一个 Cognizer 替它转交。

- **转交者**保管当前执行者的 Port：把交来的连同回话途径一起转给它，那个 Instance 直接回给发起的一方，只有去程多一跳。改指是交到它另一个 Provided port 上的一项，那个 Port 只给持有改指权的一方。它的 Journal 就是这个地址上的历史，如值班的寻呼、客服的邮箱。
- **派单者**保管几个工人的 Port，一边生产一边更新：升级时实例化新人，把新的工作派给新人，等旧人做完手上的再让它退下。每一步都是它自己的，派单的历史在它的 Journal 里。
- 转交者自己要换时：持有它的一方是 Principal 自己的，直接改用新的；否则请持有者更新：撤销旧的，交给他们新的，要持有者配合。转交者的逻辑简单，很少需要换。

## Handoff

- 由 Principal 做：构造新的 Definition，试跑检验，实例化继任者，前任暂停后不再解除暂停，或收尾后结束。前任的东西怎样到继任者那里，按 Instance 里 Handoff 的分界。Charter 的成员不换：要换的是整个 Collective，或某个成员委托出去的 Agent。
- 给继任者整理过的结果，不给前任的原始轨迹：早先的信息会压制后来的，目标会被表面线索带偏。
- **试跑**给 Principal 用：在不影响真实工作的情况下运行候选的 Definition，对比结果。

## 历史分支与合并

版本化不是一个机制：Agent 可以在自己的目录 Bundle 里放仓库，经 exec 自己用；Principal 也可以在自己的组合里另做一层。这一节说的是后者。

对话历史与文件版本共同管理，历史分支与合并保持拓扑同构，避免对话回到过去而已采用的 Bundle 仍留在后来的状态。同构针对扩展选定粒度的历史视图，不要求每条消息、每次文件变化与 Journal 的每条记录一一对应。已完成的设计验证限于历史分支与合并两种操作。文件版本的存储是目录 Bundle 的 ID：工人的 Journal 记着实际交付的 Bundle，程序状态决定采用哪份，Principal 经读取就拿得到，不必另存一份内容。

- 开历史分支时，对话从选定位置分叉，文件版本用对应位置的 Bundle，各条历史分支的输入与产物隔离。
- 合并分别处理文件内容与对话上下文，并在两边记录对应的合并关系；合并后的对话历史也允许多个前驱。文件内容的两份目录 Bundle 由 git 合并成一份新 Bundle，合并关系由保管者记下，所以不需要靠保留历史分支来维持两边的形状对应。
- 这套历史管理的入口只交给 Principal。它也只能经约定的工具修改、合并，更新需要经 Agent 的 Provided port，由它决定采用。

没有采用 Git 作文件版本的存储：git 不把名为 .git 的目录当文件存，工人自带的仓库在回退时就对不上（据记忆，待核验）。git 在这里是工具与导出：合并、diff 用它，给人看的历史导出成仓库。

这就是双智能体：

- **看全局的一方**是 Principal：经 Look 读工人的对话，只读取得工人的 Bundle 看部分代码；持有开历史分支、回退、合并的工具，以及暂停与实例化。根经 root entry 对话的是它。
- **看细节的一方**是工人，一个普通的 ReAct。它不知道有历史分支，由结构保证、不靠提示：Instance 不换 Definition，每条历史分支是一个新的 Instance，只看得到自己这一生；它也不持有历史管理的 Reference。

从历史位置开出新 Instance，就是普通的实例化：Principal 经 Look 读出那段历史，把那个位置采用的快照写进 input，并经 dependencies 交付，把那段上下文（原样或整理过）作为 Signature 的 in；新的 Instance 有自己的身份，权利只来自接线，不重放原来的 Journal，也不用 Journal 的「分叉」。

## 待定

- 保管者的合并规则。正文给了默认：路径不同直接合并，冲突按内容的规则处理。候选与 Runtime 的「并入的规则」一致：当前的 Bundle 没变就采用交回的 Bundle，变了就三方合并或报出冲突。保管者是一个长驻的 Instance，写法与持续沟通相同，见 Runtime.md 的待定。没有场景：首刀没有几方共同编辑。
- 试跑与固化：Principal 改 Agent 的工作方式，要在相同的输入与初始 Bundle 上运行候选的 Definition、对比行为；学会的做法什么时候固化成新的 Definition。试跑不影响真实工作靠接线：试跑的 Instance 只接假的或录下的 Port，不接真的出站，效果只经 Port。Journal 的「分叉」只能沿用同一份 Definition，用不上。对比什么、什么时候触发固化，待定。场景：改进循环。
- 分身（占位名，业界叫 fork subagent）：从当前位置开出新 Instance，Principal 以用户的口吻交来一项子任务，做完按规则并入交回的结果。不用另写提示词，分身与 Principal 共用前缀，前缀的计算得以复用。没有场景。
- 合法的续接位置：从一段历史开出新 Instance，位置要在协议闭合处：最近一次响应的 call 都有配对的 result；input 之后、不含 call 的完整响应之后、通知之后也合法。响应内部不合法，选中则解析到之前最近的合法点；被放弃或 unknown 的一步不算完成，不作前驱。Journal 的「任意前缀都是真实经过的某个状态」对 Instance 成立，对「把前缀喂给 llm」不成立。在最新位置发话是交到运行中 Instance 的 Provided port，在历史位置发话是从那里开出新 Instance 再交，由 root entry 区分；位置无效时报什么、谁来决定，要走一个场景（旧稿，推断；provider 要求 call 后紧跟 result，待核验）。没有场景。
- 上下文雕塑：选中一段冗杂的历史，重构出一版合并了部分步骤的过程；不是压缩，几乎不丢细节。它不改正在运行的工人，产出一版新的初始上下文，交给从那段历史开出的新 Instance；是 Handoff「给整理过的结果」的一种做法。场景：W0 持续对话。
  - 不丢细节的候选约束：模型自己的叙述可以改写、合并、删去；每个工具结果必须原样来自 Journal 里的一条记录并指向它，由程序逐条比对。这样世界给出的部分有保证，只有叙述是重写的。放不放宽为「原样，或带出处指向的派生」，见 Runtime.md 的待定。
  - 雕塑出的步骤以工人自己的过去出现，还是以别人交来的整理出现。前者更自然，也合「不知道有历史分支」；后者更诚实。候选是前者，条件是上一条约束成立。
- root entry 与磁盘上的仓库：导入时带不带 .git、跳不跳被忽略的文件，是它的做法。导入之后仓库被外界改了，写回时怎么办，现有场景没写这一步。候选：以导入时的 Tree 为基准三方合并，或拒绝并报告；外部的变化作为一项到达（一份 Bundle 加说明）交给主人，由主人并入，这要 Port 的待定「自己算出的内容」；写回以 Bundle ID 为幂等键，崩溃后重写同一棵 Tree 收敛。冲突在目标侧怎样解决，旧稿也没答（推断）。没有场景。
- 历史视图：哪些查询从 Journal 投影出来，如工作的历史、对话、谱系；以一次 LLM 调用为界的一步，与处理一个输入的连续的步（候选名 Step、Run）。前端的视图也从这里投影。Kernel 一侧只给读取，读取的粒度见 ../Kernel/Port.md 的待定。历史管理的其他操作是否保持「历史分支与合并」的同构，仍需逐项验证。场景：审计。
- Principal 观察 Agent 的进展，共同前提是增量追加，不反复注入完整历史，承载有三种：每一轮结束追加（粗）；每一步追加，判断无问题后用雕塑收拢已观察的过程（细）；一个固定字段承载更新后的当前概况，原始信息过大时先经 LLM 总结。第三种就是 Runtime.md 待定里的固定块。固定字段以当前值呈现，如常驻的仪表盘，不以消息流累积；重新订阅时先给当前的完整状态。成本与细节保留要实验（旧稿，推断）。场景：W0 持续对话。
