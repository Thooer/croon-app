# 提示词工程

人与 LLM 协作时，话怎么写。下面两条来自用户的经验与草稿转述的说法，没有对照原文，也没有做过试验，全部待核验，只作线索。每条分研究观察与我们的推断。

## 措辞的强度跟着把握走

研究观察（出处待补）：

- Sycophancy（谄媚：顺着对方的话说）在评审任务里表现为非收敛的循环（flapping）：意见随用户的反应来回摇摆。
- 要求模型说明自己的把握，可以缓解。
- 设计类任务没有标准答案，模型的改动可能是据新约束更新，也可能只是顺着语气让步；只记「模型改了什么」，会把顺从当成有效的协作。多轮里的谄媚会逐轮累积。

我们的推断：

- 把握不是每个观点一个数。标出这个观点周围的观点，以及对整场讨论的把握。
- 用措辞的强度表达把握：推出来的直说，推断的说「推断」，猜的说「猜」。写成做什么：用措辞的强度代替统一的肯定语气。比起数值，措辞不要求读者记住刻度，对各种模型都能用，这一点没有验证。
- 前提.md 记着模型报告的把握不会自动用来调节自己的推理，所以措辞承担的是给读者的信号，不指望模型靠它自我纠正。借鉴组织.md 记着展示置信度没有改善人对 AI 的监督：措辞对人读者有没有用，要单独验证。

## 用立场代替命令

前提（用户的判断，没有验证）：

- 讨论与分析一个问题时，人相比 LLM 的优势是长期记忆形成的稳定意图与立场。LLM 本身没有跨调用的连续性，这是架构上的缺口。
- 同一类任务里，知识储备与推理，人一般不如 LLM。这是工作假设，不是对所有任务的结论。

我们的推断：

- 命令把人的观点与做法当成确定的事交给模型。人的观点可能是错的，模型顺从，就被带偏。立场、想法、建议、问题传达的是意图，模型理解之后可以用自己的知识去检验，发现冲突就指出。
- 所以用立场、想法、建议、问题代替命令。立场只给方向，不规定过程，也不限制模型的行动。这条规则属于怎么写认知模式与提示词：交给模型的是意图，不是做法。仓库里没有另立一条规则，见 AGENTS.md 的「唯一出处」。
- 这条规则把方向留给人，把怎样推进留给模型，要求模型自己把局部拼成整体。所以它的前提是选能抓大放小、遵循第一性原理、有抽象审美的模型。
- 风险：追求局部正确性的模型，长周期开发里每一步都对，整体却越堆越乱，最后推不动。立场只管方向，管不了模型自己的偏好，所以选模型是这条规则成立的条件。

## 待验证

- 怎样判断一个模型抓大放小、有抽象审美，而不是凭印象选。
- 立场式的表达是否真的比命令式更少被错误观点带偏，用同一批任务对照；每轮分开记「模型改了什么」与「用户事后是否认可」。
- 两条规则一起用的效果：立场式的话里，措辞强度会不会也让模型过度顺着听上去更确定的一方。
