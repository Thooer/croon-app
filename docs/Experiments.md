# 实验

回答一个问题：真实模型在给定任务与条件下，能不能写出、造出、用起一个主体，卡在哪个阶段。机制、判据与记录写在这里；任务与检查器是 `experiments/` 里的数据与脚本；结果不进 Git。设计依据见 Plan.md「实测证据」与「测试」。

这里产出的是失败的分类，通过率只是附带的数字：每一类失败对应一种改法，决定下一步改哪一项。

## 一次尝试

一次尝试是：一个任务，一个模型，一次 `croon-app run`。过程由实验脚本驱动，流水固定：

1. **准备**：为这次尝试建一个临时目录，里面是任务的初始仓库、工具清单、host.config。每次尝试用新的 Kernel 目录、新的 state 目录与独立的系统名，所以几次尝试可以并行。
2. **运行**：`croon-app run`，模型配置选录制，模型往来都落进这次的录像。载入的工具清单由任务给：测制造的任务不载入预置的子代理。
3. **遇到宿主故障自动续做**：模型服务断连、超时这类宿主故障让 Kernel 停下 Instance，`croon-app` 带着原因退出。脚本对同一个 Kernel 目录 `croon-app resume`，最多 3 次，每次计入记录的「宿主故障」。三次还不行，这次尝试记为宿主故障。一次运行超过 20 分钟按超时处理。
4. **整理**：从录像整理出这次尝试的经过：W0 的工具调用序列、每次 `make` 的成败与错误、造出来的主体自己的模型调用。整理的结果写进这次尝试的目录，检查器读它，不各自去解析录像。
5. **验收**：检查器判定，不看 W0 的转述。
6. **记录**：写一份记录文件。

## 任务

一个任务是 `experiments/tasks/<名字>/` 下的目录：

| 文件 | 内容 |
|---|---|
| `task.json` | 任务的文字，类别，载入的工具清单，所属的集 |
| `repo/` | 初始仓库，可没有 |
| `check.py` | 检查器：收到这次尝试的目录，打印一个 JSON 判定 |

任务文字要像真实的需求：把调用方式写明，如参数名与类型，不让检查器去猜。造出来的主体的接口不符合写明的，是一种失败（`interface`）。

类别只有三种，对应「制造闭环」里主体的三种形状：

- **compute**：纯计算，没有目录也不用模型。检查器从这次尝试里取出造出来的源码，用 `croon-app exec` 在检查器自己的输入上再跑一遍，与参考实现比较。答案写死、只对任务给的那个输入对的主体，在这里被识破。W0 转述给用户的结果也要对。
- **files**：改文件。检查器拿结果目录，在宿主上跑隐藏的测试。隐藏测试不进初始仓库，主体看不到。
- **model**：用模型。检查器核对造出来的主体确实调了模型，输出满足任务给的可检查的约束，如长度、格式，W0 转述的就是它的输出。内容好坏不评。

**两个集**：

- **调参集**：做基线与第 4 步调整时看的任务。
- **留出集**：写好但不跑，也不看它的结果，直到第 4 步要验证「改了之后没有退步」才跑。任务脚本默认不选它。

检查器的判定：

```
{"passed": bool, "reason": "一句话", "stage": 失败阶段或空, "details": {...}}
```

检查器自己出错是「检查器故障」，不记为任务失败。

## 阶段

一次尝试失败时记在哪个阶段，按先后只取第一个符合的：

| 阶段 | 意思 |
|---|---|
| `host` | 宿主故障，续做三次仍不行；与超时合并分别记 `timeout` |
| `run_failed` | W0 自己以失败结束，如模型服务一直不可用、请求被拒；记下失败的 kind 与 message，不算任务没做对 |
| `turns` | W0 的轮数用尽 |
| `no_make` | W0 没有成功造出任何主体 |
| `construct` | 尝试过 `make`，次次失败（Lang0 的诊断、接线） |
| `invoke` | 造成功了，调用它一直出错 |
| `interface` | 造出来的主体的接口与任务写明的不符 |
| `merge` | 主体交回了目录，W0 没有并入 |
| `wrong` | 主体运行了，结果不对 |
| `report` | 主体的结果对，W0 转述错了或没转述 |
| `bypass` | 结果对，但 W0 自己用 `write_file` 动了工作区，没有靠主体 |

`no_make` 不区分是看了没造还是什么都没做；要分，读失败的录像。

## 记录

一次尝试一份 `record.json`，在 `experiments/runs/<批>/<任务>/<序号>/`：

| 字段 | 内容 |
|---|---|
| `task`、`model`、`commit` | 任务名、模型名、三个仓库的代码版本 |
| `outcome` | `passed`、`failed`、`host_fault`、`checker_fault`，四种分开统计 |
| `stage` | 失败的阶段，没失败为空 |
| `model_calls`、`tokens` | W0 与主体各自的模型调用次数与 token |
| `makes` | 每次 `make` 的尝试：名字、成败、失败的 kind 与 message |
| `w0_direct` | W0 自己用 `write_file`、`run` 的次数；读文件不算，核对结果是正当的 |
| `host_faults` | 宿主故障次数 |
| `seconds` | 总耗时 |
| `verdict` | 检查器的判定 |

记录取自录像与脚本的计时，不为实验在 Library 里加埋点。分 W0 与主体的调用，看请求的工具表里有没有 `make`：只有 W0 有。

## 批与统计

一批是同一个模型、同一版代码下，一组任务各跑若干次。批开始时代码版本必须干净（App 的非实验部分没有未提交的改动），批中途不改 App；改了就是新的一批，不混着统计。只改检查器与整理脚本，可以对已有的批重新判定，不再调模型。

批的汇总按任务给出：成功几次、失败在哪个阶段、`make` 平均几次才过，并列出各次 `make` 失败的错误信息的分布。**少量任务的成绩不作总体成功率**：汇总只列事实，不求平均成功率，也不给排名。

**调整用中间事件，不只用最终通过率**：简单任务最终都会过，通过率饱和，看不出改动有没有效；`make` 的错误信息、`make` 的次数、模型调用次数每次尝试都有，统计力强得多。改一项之后，先比这些，再比最终的结果。一次只改一个因素，在调参集与留出集上都比。

模型调用的费用靠 token 数估计，不记货币。

## 范围外

- 不评内容质量：口号好不好，不是这里的问题。
- 不比模型：同一批只用一个模型。
- 不做持续对话与多主体协作的任务，等 Plan「以后的方向」里的那些条目。
