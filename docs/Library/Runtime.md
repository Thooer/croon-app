# 运行

ReAct、工具、工作区、交办与 Middleware：一个主体怎样做事，以及从外面能在哪三处插入。

## ReAct

Library 里的一个函数，不是 Definition：它收工具，工具是函数，而 `main` 的参数只有值、Port 与 Inbox。用它的 Cognition 从body.modules 里 import 它，见 croon-lang0:docs/README.md「模块」。参数：

- `generate`：引擎本身，或 Middleware。
- `tools`：函数的列表；交给模型的说明从函数推出，见「工具」。
- `messages`：初始的消息历史，任务是第一条。从一段历史开出新 Instance，就是传不同的 messages。
- `system`：系统提示。
- `inbox`：收消息的 Provided port，每轮不等待地取一次；一次性交办不给。等结束的通知交到另一个 Provided port，否则会被每轮的取取走。
- `max_turns`：循环上限，就是一个 for 的轮数；默认值要实测，与 Lang0 的 B、L、W 一起定，见 croon-lang0:docs/Evaluator.md「待定」。

做法：

- 循环携带消息历史。开始时对每个工具调一次 `croon.tool`，名字与说明都从那里来，见「工具」。每轮让引擎生成一次；模型选了工具，就按工具名找到工具对象调用它；每个工具调用都接住失败，失败作为数据交还模型。limit 不在其中：它让这个分支以失败结束，接住后也空转不了，见 croon-lang0:docs/Evaluator.md「资源」。
- 一轮里的几个工具调用按顺序执行：每个工具调用有明确的输入快照，外层状态决定采用哪个产物。
- 没有工具调用就结束，回答是这一轮的文本。到循环上限仍未结束，以失败结束。
- 输出被截断（finish 为 length）、被过滤、provider 报错：以失败结束，不续写。模型没有自己的检验，截断后续写会在不完整的前因上接着推。
- **上下文管理是 ReAct 的基本功。** 历史属于 Implementation，从外面不改。上下文只放当前值；整理历史由 ReAct 自己做，或经 Handoff 由继任者接着做。
- **交来的消息只给通知。** ReAct 每轮不等待地取一次，把取到的放进自己的状态，只在工具结果上附一句"有 n 条新消息"；内容由「读消息」工具给出，作为工具结果进入历史。
- **petname 表。** ReAct 按「模型看到的名字极简」，把运行中拿到的东西（交办出去的 Agent、交来的回话途径）记在一张表里；交给 llm 的只有名字，模型在工具调用里也只写名字。

## 工具

**工具 = 函数 + 交给模型的说明**（名字、描述、Schema）。函数包装后交给模型选择，程序也可以直接调用它；说明不增加身份或权利。函数捕获的 Reference 就是它的上限。

- **固定的工具集**：每个工具是一个函数，要用的引用值由闭包从外层函数捕获，或用 functools.partial 绑上；交给模型的 Schema 从函数推出，见 croon-lang0:docs/README.md「Interface」里的 `croon.tool`；调用时它先查模型给的 input，返回后再查返回值。工具名只是名字，自然的说法写在描述里。需要可以从各工具的 Port 参数算出。
- **文件与命令**：read_file、write_file、run 是捕获 exec 的普通函数。一次调用就是一次交出，不起新的 Instance。file_tools 收一个私有工作区：每次 exec 显式交付它的当前位置，并采用交回的快照，见「工作区」。
- **版本**：diff 与合并经 exec 里的 git 做，Bundle 是否包含目录仓库由 Agent 自己决定；不新增 Kernel 的东西。
- 工具的代价与输入的大小成线性：模型给一个大输入，代价不受约束的工具就能让整个 ReAct 以 limit 失败。做不到线性的，写成顶层函数加 partial，在 ProcessPoolExecutor 的分支里跑，limit 在父分支里接得住。
- **工具目录**，用于开放的工具集：
  - 「查」：按需返回工具的说明，说明作为工具结果进入历史。卸载不需要操作，说明离开上下文就算卸载。
  - 「用」：按名字找到 Definition，实例化一个一次性的 Agent，显式交付选定的 Bundle，等它结束，按规则采用或合并它交回的 Bundle。它本身是一个函数：实例化、取与并入都是它发出的 Atom；它产生一个主体，它自己不是主体。
  - 只列出自己接上的东西覆盖得了的工具。
  - 它要用 instantiate，所以由 Principal 决定给不给。"动态增加工具"就是给这个。
  - 代价：用不上 provider 原生的工具调用。好处：原生的工具列表不变，前缀缓存不失效。
- **构造与交办**：构造 Definition；交办（实例化，立即返回）；等待（向 Notify 登记，再取）；查看（不等待）。

## 工作区

工作区是一个主体当前采用哪份目录 Bundle 的可变位置，加上从它派生候选、把候选并回来的规则。目录 Bundle 不可变，相当于提交；工作区是指向它的可变位置，所以必须有主人，每次移动由主人的 Journal 解释。Kernel 不提供默认工作区，见 croon:docs/Kernel/Instance.md「程序状态」；工作区是 Library 的概念。

- **私有工作区**是 Library 的库函数，主人是调用它的 Instance：当前位置是 body 携带的状态，每次移动是一次执行结果加一次采用，重放即恢复。它没有自己的身份，用调用方的权利。文件工具、交办与并入都经它，不各自持有快照。
- **共享工作区**由保管者承担：持有当前位置，开读当前、提交候选、合并的 Port，见 Organization.md 的「共享与保密」。它是一份 Definition，有自己的身份与 Journal。见待定。

派生与并入的规则：

- **派生**：交办或并行执行前，从当前位置记下 base；执行交回 candidate。两者记在调用方给的名字下；名字重复时加序号，不覆盖已有的。base 在执行之前登记，还没交回 candidate 的不能并入。
- **并入**：当前位置等于 base 时采用 candidate；否则显式请求 exec 三方合并，得到另一个候选，合并失败以失败交还，当前位置不变。调用方检查后才移动当前位置，Kernel 不自动采用。命令失败也可能有稳定产物，程序明确决定采用或保留。只拿交回仓库里的提交，不在它的目录里运行命令；它的配置能影响执行。没并进去、没提交或被忽略的内容要报给模型。
- **跨调用保留的只有 /work**：镜像根只读，/work 之外的改动不进产物。依赖装进 /work 或预先做进镜像；文件工具的说明要告诉模型这一点。

## 交办

- **一次性交办**：实例化，把选定基准 Bundle 放进 input 并经 dependencies 交付，等它结束，按规则采用或合并交回的 Bundle。可信的工具自动并入，在模型看来是一个普通的工具。
- **审阅改动**：采用之前，先检查交回的 Bundle，像审阅一个 PR；Bundle 带仓库时，就是看两个提交之间的差。不可信的拆成两个工具：交办返回总结与改动，把交办时的 Bundle 与交回的 Bundle 记在模型给的名字下；采用或合并是另一个工具，按名字取出这两份 Bundle。两次之间模型可以调别的工具。
- **并入**按「工作区」的派生与并入规则。
- 交办的 out 给出总结与 snapshot，main 用 deliver 交付该 snapshot；通知的 dependencies 沿结束结果转交。Definition ID、基准与结果 ID 由 petname 表保管，模型只见交办名字与结果。
- 一次性的辅助程序要足够便宜：不需要目录服务就不准备目录输入。
- 交办类的 Interface 按要什么声明指向自己的 Reference，实例化的一方用 self 把它接到自己的 Provided port 上：要等结束的声明 done，收结束状态，向 Notify 登记时附带它；要反问的声明 me，收消息。两者形状不同，权利也分开：能交来消息的一方冒充不了结束。
- 常用的 Port spec 由 Library 给出，如结束状态、回话、只能暂停的 Correct。接收方的声明要与链上某一节相同，所以两边都引用同一份。
- **委托不超过两层**：默认让 root entry 实例化的 Agent 还能交办，它交办出去的任务 Agent 不再接 instantiate。这里计模型逐层解释、拆分与转述任务的委托链；工具目录运行的固定辅助流程、Collective 的成员关系不计入这条链。限制深度是为减少逐级语义误差与原始轨迹携带的目标漂移；Control 也不沿实例化往下够。这只是默认接线：Principal 要更深，就把 instantiate 接下去；附带声明限定了能取得哪些 Reference 时，实例化路径的上限可从结构检查。共享高层信息与 Charter 能否支持更深的委托，见待定「委托的深度与共享」。

## Middleware

Middleware 是作为参数传进内层的函数，代替它本来要用的 Port，例如在 engine 前压缩请求。它使用同一个 body 的权利，只约束经过它的调用，Reference 转交出去，包装不跟着走；要跟着 Reference 走的收窄，用限定。

要跨 Instance 共享状态或隔离权利，就接保管者，不是 Middleware。例如全组预算的计量者保管引擎与累计用量，超额就拒绝；学术库的限流者保管检索的 Reference，供所有检索者共用。

## 待定

- 输入注入：交来的、变化的东西怎样呈现给模型，分三维（旧稿，推断）。场景：W0 持续对话。
  - 性质：消息（谁说了什么）、状态字段（当前状态）、指令变更（工具或系统提示变了）。交来的消息只给通知，通知附在工具结果上时，输出是字符串的就要包一层，模型看到的形状随之变，这是 ReAct 自己的选择。
  - 时机：ReAct 一轮还在进行时交来新消息，保留这一轮的结果、只附上通知（现在的做法），还是丢弃这一轮、带上新消息重调；前者可能按过期的计划多走一步，后者丢掉一次已经花了钱的调用。模型已经给出最终回答、还有没读的消息时，通知附不到工具结果上，怎么办。暂停与追加输入本来分开：在当前步完成、下一步开始前暂停，追加与解除暂停可分别表达，也可组合成「发送并继续」；普通发言是否自动解除暂停是策略。
  - 位置：消息列表，或固定块：每次请求从当前的事实重新算出，放在请求末端，声明自己是派生的、不进消息历史，所以前缀不变。计划与上下文占用是它的两种内容，见下两条。
- 计划与任务：计划是 Task 工具维护的数据，创建任务不要求调用子代理；调用子代理必伴随一个对应的任务，它在已有计划里怎样安排由发起委托的 Principal 定。计划轴与消息轴分开：消息可以整理，计划不压缩、不降级，每一步呈现在固定块里；装不进窗口是请求失败，出路是拆分任务，不是压缩计划。状态只有 pending、running、succeeded、canceled，没有 failed；每次改一个任务并带 expected_revision；父子表达分解，前驱后继表达同一父任务下的顺序；子代理完成就是父任务少一个未收口的子节点。「当前计划节点」是路径级的焦点，并发的几条路径各有各的（旧稿，推断）。没有场景：首刀用不到。
- 让模型知道上下文占用与预算：每次重新提供窗口容量、当前占用、压缩阈值（暂名 context_state），放在固定块里。窗口容量要能从接上的模型读到，见 croon:docs/Kernel/Port.md「待定」里的「一个 Reference 对外透露提供者的哪些事实」。给比例还是绝对值、任务用量的分母怎么定，待实验。压缩时机候选：在较大的工作边界附近结合阈值提醒收尾，再调压缩工具；达到阈值不等于必须立即压缩（旧稿，推断）。场景：W0 持续对话。
- 上下文管理怎样替换。候选：body 决定何时整理、采用哪些结果，整理做法封装成 Library 调用，通过接线替换；共享的长期记忆由保管者持有。用具体场景检验调用与接线是否够用，以及出处怎样呈现给模型。离线的整理，即把一段历史整理成新的初始上下文，见 Organization.md 的待定「上下文雕塑」。场景：W0 持续对话。
- 响应的形状：一次响应整体归入且只归入一种：继续（一个或多个工具调用）、等待（反问，独占一轮）、完成（无调用，正文非空）。混排或空的完成，整体无效，不执行其中的子集。对照 ReAct：反问与别的调用同轮出现时，「按顺序执行」会让后面的调用等一个没来的回答；空回答（finish 为 stop、无文本也无调用）按现在的规则是一个空的回答。候选：混排时整体拒绝并让模型重新生成；空回答按失败，或重试一次，每次尝试有自己的键（旧稿，推断）。场景：委托中途反问。
- 失败按 kind 区别对待：denied、type 说明这条路走不通，交还模型时不鼓励重试；外部世界偶发的失败可以重试，写法见 croon-lang0:docs/Evaluator.md「求值」。读出 kind 要 croon-lang0:docs/README.md「失败」。场景：B 交来消息并附带回话途径。
- 失败时问处理者：Middleware 接住一个 Port 的失败，经反问（见「交互的封装与写法」）交给接线指定的处理者，如 Principal 或 Charter 写明的成员，按回答重试、换输入、跳过或改走别的路；栈没有展开，回答到了就接着走。Kernel 一侧的重启只有暂停、收回、授予、解除暂停，不替 body 换输入或跳过：那样记下的 Atom 与 Language 报出的不同，违反「一个键只对应一个 Atom」；Correct 也从换接上的东西变成改 body 的路径，违反「量变攒不成质变」。场景：委托中途反问。
- 系统提示要不要告诉主体：除了调用接口，它的所有思考和输出都不会有人看见（用户的设想，没验证）。没有场景：随 Plan 的「LLM 表现量化」验证。
- 工具少而通用，还是多而专门。没有场景。
- 文件工具的前置条件：读返回内容的 hash，即这个文件在目录 Bundle 里的内容 ID；写与改必填 expected_content_hash（目标不存在时用字面量 absent），不符就不执行，返回独立的错误。能防模型按过期的读去写、并行分支互相覆盖，不需要新的 Kernel 机制（旧稿，推断）。读 ID 可以用 read_json/read_text 或经显式快照的 exec 算。场景：Delegate，并入之后按并入前的读去写。
- 交办是不是一个固定的工具：现在是根把子 Agent 的 Definition 写进 W0 的 input，模型只写任务；工具目录的「用」是模型按名字选。区别在模型调交办时，要不要自己选 worker 的 Definition。首个场景的写法见 Presets.md 的待定「首个场景里 W0 的写法候选」。场景：运行中构造再实例化。
- 交互的封装与写法。场景：W0 持续对话、委托中途反问、B 直接问 A。
  - 子代理即交办，不需要持续的验证与沟通；持续沟通如长期的 Agent、对话，配套持续的验证。两者在沟通次数上是一与多，别的差别由需要决定。多方沟通要不要统一的封装：原想法是 ANA，用主体之间的这套原语组装出 A2A、ACP、ANP 一类协议的功能；沟通的总称候选 Communicative act（沟通行为）。外部协议在系统边界上的绑定见 croon:docs/Kernel/README.md「待定」里的「系统边界」。
  - 写法候选，用 Lang0 的取与引用值：持续沟通与保管者的服务都是一个 while，每一轮取一项到达，由状态与它算出新状态与要发出的 Atom。交办的写法固定，引用的类型来自 Kernel 给的 Port spec，模型不写。
  - 反问：一个辅助函数，交出时附带指向自己某个 Provided port 的 Reference 作回话途径，再按回执里那一份的 Handle 取回答；不按 via 取，上一个问题超时后迟到的回答会被当成这一个的。取到回答后用撤销权撤掉那一份，之后沿它交来的被拒；要 Kernel 保证对方只回一次，用 croon:docs/Kernel/Reference.md「限定」里的限次保管者。提示词与它要的 Schema 合写在这个辅助函数里。
  - 作用域内的撤销：辅助函数附带出去，用完拿撤销权撤掉，出错时靠 finally 撤掉；with 已放开，可以写成 with，退出时撤。Kernel 结束 Instance 或换代际时 finally 不运行，撤销权留在已结束的 Instance 里。
- 委托的深度与共享：共享高层信息与 Charter 可能支持更宽的扇出、更深的委托。高层信息由谁提供、怎样避免逐级转述、谁持有下层的 Control，随场景定，与 Handoff「给整理过的结果」一起看；不预先认定共享就消除了误差。Charter 的 Signature 只把输入给一个 Seat，其余成员仍要经 Port 得到。场景：外包的嵌套、公司的采购成员外包给供应商。
- 两个 Instance 互相无限期地等会死锁：Library 里等别的 Instance 是否都设上限。机制已有取的 timeout，不设就一直等，如等一个结束状态。有一方卡住时，别的一方只能靠自己的上限发现它不再前进，因为系统里没有「卡住」这个信号，见 croon:docs/Kernel/Journal.md「恢复就是重放」。第三方要查出死锁，得看见谁正在等什么：在途的取没有记录，与 croon:docs/Kernel/Reference.md「待定」里的「在途 Atom 的事实」缺的是同一样（推断）。场景：委托中途反问、B 直接问 A。
- 共享工作区的写法：分支表的形状、谁能移动哪个分支、并入冲突怎样交还。与 Organization.md 待定里的「保管者的合并规则」一起定。场景：几方共同编辑一份代码。
